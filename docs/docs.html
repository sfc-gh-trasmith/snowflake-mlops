MLOps on Snowflake

GuideOpen-source template

Build, validate, promote, serve, and monitor machine learning models across development, staging, and production environments, with Git as the system of record and Snowflake as the platform where data, features, models, and inference live together.

MLOps is the set of practices that makes machine learning repeatable and safe in production: every model is traceable to the code and data that produced it, every promotion passes automated checks and a human approval, and production models are monitored and can be rolled back. On Snowflake, these practices run where the data already is: feature pipelines, training jobs, the model registry, inference, and monitoring are Snowflake objects, governed by the same roles and policies as your data.

You can build and run these workflows yourself, or use agentic ML with Snowflake CoCo to generate and run them from natural-language prompts. Either way, the practices in this guide apply.

This guide has two parts:

  • MLOps on Snowflake: the lifecycle, a reference architecture for dev/stage/prod with a Git workflow, and how responsibilities split between personas.
  • The MLOps template: an open-source project that implements that architecture end to end, with an in-depth look at how it orchestrates training, gating, promotion, serving, and monitoring, and how to adopt it.

The ML lifecycle on Snowflake

Each stage of the lifecycle maps to a Snowflake ML capability. Because they share one platform, the handoffs between stages (features to training, training to registry, registry to inference, inference to monitoring) are object references rather than file exports.

Lifecycle stageSnowflake featureDescription
Data validationVirtual warehouses (SQL)Elastic compute clusters that run SQL and Snowpark queries, so you can check row counts, null rates, and freshness before training.
Feature engineeringSnowflake Feature Store and dynamic tablesThe Feature Store registers entities and feature views, with point-in-time correct training sets and online serving. Dynamic tables are declarative tables that Snowflake refreshes incrementally to a target lag.
Training dataDatasetsImmutable, versioned snapshots of query results, so each model version can be traced to the exact data it was trained on.
TrainingSnowflake ML Jobs or Snowpark stored proceduresML Jobs run Python on the Container Runtime, on CPU or GPU compute pools. Snowpark stored procedures run Python on warehouses.
Experiment trackingExperimentsExperiment objects group training runs and store their parameters, metrics, and artifacts, so you can compare runs and select a model.
Model managementSnowflake Model RegistryModels are schema-level objects that hold versioned, packaged models with metrics, metadata, aliases, and a default version.

Reference architecture: environments and Git workflow

This section describes one recommended approach, not the only way to run MLOps on Snowflake. It works well for a typical tabular model that needs batch and real-time scoring. Use cases differ in data volume, latency, regulatory requirements, retraining cadence, and team structure, so treat it as a blueprint to adapt rather than a standard to copy.

At a high level:

  • Three environments, isolated by database. DEV, STAGE, and PROD each have their own database, warehouse, compute pool, Snowflake Feature Store objects, and Snowflake Model Registry models. Production source data lives in PROD and is read-only to DEV and STAGE, so every environment works on real data but writes only to its own database.
  • Git drives every change. Code, feature definitions, configuration, and real-time traffic weights are committed. A CI/CD system (for example, GitHub Actions) deploys to STAGE on every merge to main and to PROD only after a required reviewer approves.
  • STAGE trains; PROD serves. STAGE builds features from production data, trains the model, gates it on quality thresholds and against the current PROD model, then registers it and validates batch scoring and monitoring. PROD does not retrain. It receives a copy of the exact model version that passed in STAGE.
  • Two serving paths in PROD. Batch: a scheduled task scores the PROD feature view and writes predictions tagged with the model version. Real-time: each model version runs as its own inference service on Snowpark Container Services behind a gateway, so traffic can shift gradually between versions behind one stable URL.
  • Monitor, retrain, roll back. ML Observability model monitors track drift and performance in PROD. A scheduled retrain (for example, weekly) produces a new candidate in STAGE, and a rollback workflow restores the previous model and traffic split if needed.
  • Governance across all environments. Least-privilege roles per environment, OIDC sign-in for CI with no stored secrets, approval gates on PROD, and lineage that links each model to its dataset, feature view, and Git commit.
Adapting the baseline

Common variations: fewer environments (DEV and PROD only) for low-risk models; separate Snowflake accounts instead of separate databases for stricter isolation; retraining in PROD where data cannot leave it; batch-only or real-time-only serving; or an external orchestrator in place of Snowflake tasks. The design principles below matter more than the exact layout.

For the deployment steps behind this architecture, see Deploy models end to end.

Design principles

  • Git is the source of truth. Feature logic, training code, configuration, and real-time traffic weights are all committed. Environments are rebuilt from the repository, not edited by hand.
  • Train where you deploy from. The candidate promoted to PROD is the exact model version trained and validated in STAGE; promotion copies that version rather than retraining it.
  • Automated checks, human decisions. Code quality, data checks, metric thresholds, and champion comparison are automated. Promotion to production requires an explicit approval.
  • Everything is versioned and traceable. A production model version links back to its training dataset version, feature view version, experiment run, and Git commit.
  • Least privilege per environment. CI uses separate roles for STAGE and PROD and authenticates with OIDC, so there are no long-lived credentials in the repository.

Deploy models end to end

The reference architecture describes where each step runs. This section covers the deployment decisions you make for each model: which inference option to use, how to package the model for it, how to promote an approved version, how to supply features for real-time inference, and how to roll out, monitor, secure, and pay for deployed models. For preparing pipeline code, orchestration, and CI/CD setup, see Create pipelines and deploy them.

Before you begin

  • A trained model logged, or ready to log, in the Snowflake Model Registry with the snowflake-ml-python package.
  • A database (and schema) per environment, with a role per environment that owns its models.
  • For real-time inference: a compute pool, and the BIND SERVICE ENDPOINT privilege on the account to create a public endpoint.

Choose an inference option

The Model Registry serves every registered model through one interface, backed by two compute engines: warehouses and Snowpark Container Services. Choose the option that matches your latency, data, and scaling requirements. Many production models use more than one; for example, nightly batch scoring plus a real-time endpoint for an application.

OptionUse it whenData sourceRuns on
Native batch inference (SQL)Predictions feed SQL pipelines, such as dynamic tables, tasks, or dbt modelsSnowflake tablesWarehouse
Job-based batch inferenceHigh-volume or unstructured workloads, such as images, audio, or large backfillsFiles in Snowflake stagesSnowpark Container Services
Real-time inference (REST API)An application needs low-latency responses per requestSmall payloads sent over HTTPSSnowpark Container Services

For a detailed comparison, see Model inference in Snowflake.

Package a model for its target platform

A model version can run only on the platforms it was logged for. Decide the inference option before you log the model, and set target_platforms when you call log_model:

  • WAREHOUSE for native batch inference in SQL.
  • SNOWPARK_CONTAINER_SERVICES for real-time inference and job-based batch inference.
  • Both, if the same version serves batch and real-time traffic.
from snowflake.ml.registry import Registry

reg = Registry(session=session, database_name="ML_STAGE", schema_name="MODELS")
mv = reg.log_model(
    model,
    model_name="FRAUD_MODEL",
    version_name="V7",
    sample_input_data=train_df.select(feature_cols).limit(100),
    target_platforms=["WAREHOUSE", "SNOWPARK_CONTAINER_SERVICES"],
    metrics=eval_metrics,
)

Pin the Python packages the model needs and log a sample input so the registry records the model signature. To check where an existing version can run, use SHOW VERSIONS IN MODEL and look at the runnable_in column. For details, see Snowflake Model Registry.

Promote a model between environments

Promote the exact version that passed validation instead of retraining it in production. The implementation inside a model version is immutable, so a copy runs the same model you tested.

  1. Copy the version into the production registry. Create the model in the production schema from the validated version, or add the version to a model that already exists there: 
    -- First promotion: create the production model from the validated version
CREATE MODEL ML_PROD.MODELS.FRAUD_MODEL WITH VERSION V7
  FROM MODEL ML_STAGE.MODELS.FRAUD_MODEL VERSION V7;

-- Later promotions: add the new version to the existing production model
ALTER MODEL ML_PROD.MODELS.FRAUD_MODEL ADD VERSION V8
  FROM MODEL ML_STAGE.MODELS.FRAUD_MODEL VERSION V8;
  2. Make it the version consumers use. Set it as the default version so batch jobs that score with the default pick it up. Keep the previous version: rolling back means setting the default back to it. 
    ALTER MODEL ML_PROD.MODELS.FRAUD_MODEL SET DEFAULT_VERSION = 'V8';
  3. Optionally, label versions with aliases. An alias such as production or challenger names a version by its role, so callers don't need to know version names. Moving the alias promotes or rolls back in one statement. 
    ALTER MODEL ML_PROD.MODELS.FRAUD_MODEL VERSION V7 UNSET ALIAS;
ALTER MODEL ML_PROD.MODELS.FRAUD_MODEL VERSION V8 SET ALIAS = production;
  4. Update real-time serving separately. A service runs one fixed version. Deploy a service for the new version, then shift traffic to it (see Roll out real-time model versions).

The role that promotes a version needs OWNERSHIP or READ on the source model and CREATE MODEL on the production schema. To promote across Snowflake accounts instead of databases, replicate the database that contains the validated model to the production account, then copy the version from the replica with the same commands. For lifecycle patterns that use schemas, aliases, or tags, see Managing models with the Snowflake Model Registry. For the commands above, see CREATE MODEL, ALTER MODEL … ADD VERSION, and ALTER MODEL.

Serve features for real-time inference

Batch scoring reads features from tables at scoring time. A real-time request has milliseconds, so the features must already be available when the request arrives. Use one of these patterns:

  • Read from the Online Feature Store. Enable online serving on a feature view. The application, or the code that calls the model, fetches the latest feature values per entity key and sends them with the request. Because the same feature view also produces training datasets, training and serving use the same feature definitions.
  • Send features in the request. When the caller already has every input (for example, the details of a transaction being authorized), pass them directly in the payload.
  • Combine both. Send request-time inputs in the payload, and look up historical aggregates for the same entity in the Online Feature Store.
Preview feature

The Online Feature Store is in preview and requires snowflake-ml-python 1.41 or later. For online serving with generally available features, see online serving with hybrid tables on the same page.

Whichever pattern you use, guard against training-serving skew: features computed one way for training and another way at request time. Compute features in one place (the feature view), and include a check in STAGE that scores the same rows through the batch path and the real-time endpoint and compares the results.

Roll out real-time model versions

Each model version runs as its own inference service. Put a gateway in front of the services so applications call one stable URL while you change which versions receive traffic:

  1. Deploy a service for the new version alongside the current one: 
    mv = reg.get_model("FRAUD_MODEL").version("V8")
mv.create_service(
    service_name="FRAUD_MODEL_V8",
    service_compute_pool="ML_PROD_POOL",
    ingress_enabled=True,
)
  2. Run a smoke test against the new service: send a few known requests and check that the responses have the expected shape and values.
  3. Route a small share of traffic to it (a canary), or mirror requests to it without returning its responses (shadow traffic).
  4. Compare latency, error rates, and predictions between versions. See Gateway monitoring and A/B testing.
  5. Increase the share step by step until the new version serves all traffic, then suspend or drop the old service. To roll back, route traffic back to the previous version.

Decide the rollback criteria before you start the rollout, so the decision doesn't depend on judgment under pressure. Common criteria:

  • The error rate or latency of the new version exceeds an agreed threshold.
  • The prediction distribution differs sharply from the current version on the same traffic.
  • A business metric, such as approval rate, moves outside its expected range.

Keep traffic weights in version control and apply them from CI/CD, so every change to production traffic is reviewed and recorded.

Monitor deployed models

ML Observability computes drift, performance, and statistical metrics for a model version from logged inference data. Plan for these inputs when you deploy, not after:

  • Inference logs. A table with one row per prediction: the model inputs, the prediction, an ID, and a timestamp. Batch scoring can write this table directly. For real-time services, enable automatic capture of inference requests and responses when you create the service; the setting can't be changed later.
  • Actuals. The true outcome (the label), joined to the logged predictions when it becomes known. Performance metrics such as precision need actuals; drift metrics don't.
  • A baseline. A table that represents expected behavior, typically the evaluation data from training. Drift is measured against it.
CREATE MODEL MONITOR ML_PROD.MODELS.FRAUD_MODEL_V8_MONITOR WITH
  MODEL = ML_PROD.MODELS.FRAUD_MODEL
  VERSION = 'V8'
  FUNCTION = 'predict_proba'
  SOURCE = ML_PROD.SCORING.FRAUD_PREDICTIONS
  BASELINE = ML_PROD.SCORING.FRAUD_BASELINE
  WAREHOUSE = ML_PROD_WH
  REFRESH_INTERVAL = '1 day'
  AGGREGATION_WINDOW = '1 day'
  TIMESTAMP_COLUMN = SCORED_AT
  ID_COLUMNS = ('TXN_ID')
  PREDICTION_SCORE_COLUMNS = ('FRAUD_SCORE')
  ACTUAL_CLASS_COLUMNS = ('IS_FRAUD');

To act on what the monitor finds, create an alert that checks a metric on a schedule. The alert can notify the team, or start retraining by running the training task graph in STAGE:

CREATE ALERT ML_PROD.MODELS.FRAUD_DRIFT_ALERT
  WAREHOUSE = ML_PROD_WH
  SCHEDULE = 'USING CRON 0 8 * * * UTC'
  IF (EXISTS (
    SELECT 1 FROM TABLE(MODEL_MONITOR_DRIFT_METRIC(
      'ML_PROD.MODELS.FRAUD_MODEL_V8_MONITOR', 'JENSEN_SHANNON', 'FRAUD_SCORE',
      '1 DAY', DATEADD('DAY', -1, CURRENT_DATE()), CURRENT_DATE()))
    WHERE METRIC_VALUE > 0.2))
  THEN
    EXECUTE TASK ML_STAGE.PIPELINE.TRAIN_ROOT;

A retrain triggered this way still goes through the STAGE gate and the PROD approval, so a drift alert can't put a model into production on its own. Choose thresholds from your own baseline; the value above is only an example. For metric functions, see Model monitor functions.

Secure deployed models

Models are schema-level objects, so the same role-based access control that protects your data protects your models. Model objects have three privileges:

PrivilegeAllows
OWNERSHIPFull control: add and drop versions, set the default version and aliases, access artifacts, and update metadata.
USAGEWarehouse inference and SHOW commands, without access to the model's code, weights, or other artifacts.
READInference on Snowpark Container Services, access to model files and metadata, and SHOW commands. Needed to deploy a version to a service or to copy it.
  • Separate roles per environment. Give each environment its own role that owns its models. Production consumers get USAGE (batch) or access to the service endpoint (real-time), not ownership.
  • Control who can call an endpoint. By default, only the service owner can use a real-time endpoint. To let another role call it, grant that role the service role ALL_ENDPOINTS_USAGE.
  • Authenticate callers. Applications call endpoints with Snowflake credentials, such as a programmatic access token. Restrict where those calls can come from with network policies on the calling users.
  • Authenticate CI/CD without stored secrets. Use workload identity federation so pipelines, such as GitHub Actions, sign in with short-lived OIDC tokens instead of passwords or keys stored in the CI system.

For grant examples, see Managing models with the Snowflake Model Registry and Deploy models for real-time inference (REST API).

Cost and scaling

  • Batch inference on warehouses uses warehouse credits while the scoring query runs. Size the warehouse for the scoring job, and let it auto-suspend between runs.
  • Real-time inference and job-based batch inference run on compute pools. A real-time service scales between min_instances and max_instances, which you set in create_service. With min_instances=0 (the default), the service suspends after 30 minutes without traffic and resumes on the next request, at the cost of a slower first response.
  • Old versions keep costing money if their services keep running. After a rollout completes, suspend or drop the previous version's service, and set auto-suspend on compute pools.
  • Training runs on warehouses or compute pools, chosen per step. Use GPU pools only for steps that benefit from them.

To track inference credits by model and service, query the MODEL_SERVING_USAGE_HISTORY view.

Trace lineage

ML Lineage records how source tables, feature views, datasets, and model versions relate. Use it to answer which data trained a production model, or which models are affected when a source table changes. To link a model version to its code, also record the Git commit in the version's metadata when you log it.

Considerations

  • Decide each model's inference options before logging it, because a version's target platforms are set when it is logged.
  • Real-time features need their own serving path. Plan it with the model, not after deployment.
  • Automatic capture of inference logs must be enabled when a real-time service is created.
  • Services, monitors, alerts, and grants are separate objects, so copying a version doesn't create them. Create them in the target environment from code.
  • Keep at least the previous production version and its service available until the new version is stable, so you can roll back quickly.

Part 2

The MLOps template

The snowflake-mlops template is an open-source repository that implements the reference architecture above with GitHub Actions and Snowflake ML. It ships with a working example (a fraud classifier on synthetic data) and is model-agnostic: you swap in your own features and model, and the platform pieces (versioning, gating, promotion, serving, monitoring, rollback) keep working.

Pipeline

A Snowflake task graph: data checks and feature engineering, training and registration, evaluation and gating. Each step runs on a warehouse or a compute pool, chosen in config.

Promotion

Code-driven (merge to main) and data-driven (weekly retrain). PROD requires approval and receives the exact STAGE version.

Serving

Batch, real-time, or both. A scheduled scoring task, and per-version inference services behind a gateway with canary weights in Git.

Operations

Model monitor with ground truth, drift alerts, one-click and automatic rollback, a REST smoke test, release tags, and a job summary comparing every candidate with the champion.

Scope

The template targets a single Snowflake account with one database per environment. For separate accounts per environment, see Multi-account setup.

Template architecture

GitHub Actions orchestrates releases; all ML work runs in Snowflake. CI authenticates to Snowflake with OIDC workload identity, using a STAGE role for training and validation and a PROD role for promotion and serving. Source data lives in PROD and is read by every environment; each environment writes its own feature views, datasets, models, and results.

Training pipeline

The training pipeline is a Snowflake task graph named MLOPS_DEMO_TASK, deployed and run by source/pipeline/train_dag.py. Each step is a package under source/ exposing run(session) -> dict. At deploy time the step code and configuration are zipped and staged; each step then runs either as an ML Job on a compute pool or as a stored procedure on a warehouse, according to pipeline_steps in config.yml. Steps hand results to each other through the PIPELINE_RESULTS table.

StepDefault computeWhat it does
FEATURE_ENGCompute pool (ML Job)Runs data_checks on source tables, then registers the entities and feature views. A feature view version is immutable: if it exists with the same schema it is reused; if the columns changed without a version bump, the step fails.
TRAIN_MODELCompute pool (ML Job)Generates a new Dataset version from the feature view, trains on a grouped split, computes task-appropriate metrics, scores the PROD champion on the same holdout, and logs a new model version with lineage, metrics, and task= for ML Observability.
EVALUATEWarehouse (stored procedure)Applies quality_gate.metrics rules and the champion comparison. On pass, records the decision on the version; on fail, drops the version and fails the task.

Run the pipeline on demand from your machine:

uv run python source/pipeline/train_dag.py --deploy --env dev
uv run python source/pipeline/train_dag.py --execute --env dev

Promotion workflow

The template supports two promotion paths. Both end with a human approval before anything changes in PROD.

Code-driven

A merge to main runs deploy.yml: STAGE trains and gates the new code, then PROD waits for approval.

Data-driven

scheduled-retrain.yml retrains weekly on fresh data in STAGE and opens a GitHub issue. A reviewer promotes the candidate with deploy.yml (promote_only).

deploy-stage

  1. Deploy the training task graph to STAGE and trigger it.
  2. Wait for completion; read this run's evaluation from PIPELINE_RESULTS.
  3. Write the job summary: every metric for the candidate and the PROD champion side by side, the change, the decision metric, per-rule results, and lineage. It is written even if the pipeline fails, so rejections are reported.
  4. If batch serving is enabled, score with the candidate and validate the outputs.
  5. If monitoring is enabled, create the monitor and drift alert, verify them, then drop them.
  6. Retention: prune STAGE model and Dataset versions beyond the newest N (see Versioning and lineage).

deploy-prod (after approval)

  1. Capture the current PROD default version and gateway split, for automatic rollback.
  2. Promote: copy the gated version into the PROD registry with CREATE MODEL ... FROM MODEL or ALTER MODEL ... ADD VERSION ... FROM MODEL, copy the lineage comment, and set it as the default version. Re-running is safe: an identical version already in PROD is kept.
  3. Batch: register PROD feature views, validate scoring with the promoted version, and deploy the scheduled scoring task.
  4. Real-time: create <MODEL>_SERVICE_<VERSION>, health-check it (valid outputs, parity with warehouse scoring within 1e-4, agreement with the incumbent), then route canary_weight% of gateway traffic to it. The rest stays on the previous default version, the champion the candidate was gated against. The first deploy creates the gateway with 100% to the new version. Applying the split drops every model service that isn't a gateway target; a service that fails its health check is dropped before it takes traffic.
  5. REST smoke test: real HTTPS calls to the gateway and to each service behind it, authenticated with a one-day PAT that the job issues for its own service user and removes afterwards. Each response must have one valid prediction per row and match warehouse scoring of the same version.
  6. Sync the file: open a pull request that records the new split in deploy/gateway-config.yml. main is protected, so workflows never push to it; merge the PR to keep the file in step with what's serving.
  7. Create or update the PROD model monitor and drift alert.
  8. Retention: prune old PROD model versions.
  9. Tag the release as prod/<VERSION>-<timestamp>.
Automatic rollback

If any step after promotion fails (service, health check, gateway, smoke test, or monitor), deploy-prod restores the captured default version and gateway split, which also drops the failed version's service. Batch scoring follows the default version, so it is restored too. On the very first deployment there is nothing to restore, and the job just fails.

Persona journeys

Data scientist: ship a model improvement

  1. Explore in DEV. Use notebooks 01–03 to explore source data, prototype features, and train locally against Snowflake data.
  2. Change the code. On a feature branch, edit feature_views.py and training.py. If you changed feature columns or logic, bump feature_store.view_version.
  3. Run the pipeline in DEV. train_dag.py --deploy --execute --env dev runs the same task graph CI uses, so problems show up before review.
  4. Open a pull request. Lint and unit tests run; a teammate reviews.
  5. Read the STAGE job summary after merge: your candidate's metrics next to the PROD champion's, scored on the same holdout.
  6. Hand off for approval. If the gate passed, the approver promotes it; if not, the summary lists the failed rules.

ML engineer: operate the platform

  1. Provision. Run setup.sh and setup_cicd.sh; set the GitHub variables and environments.
  2. Choose compute and serving. Set pipeline_steps.*.compute, serving.batch, and serving.realtime in config.yml.
  3. Set the bar with the data scientist. Agree on quality_gate.metrics and the champion metric and margin.
  4. Manage the canary. After deploy-prod, raise the new version's weight in deploy/gateway-config.yml through a pull request; traffic-shift.yml applies it and drops services you remove.
  5. Watch production. Review model monitor dashboards and DRIFT_ALERTS; run rollback.yml to revert to a previous version.

Get started

Prerequisites

  • A Snowflake account and a role that can create databases, warehouses, compute pools, roles, and users (the setup scripts use ACCOUNTADMIN).
  • Python 3.11 or 3.12, uv, the Snowflake CLI (snow) with a configured connection, and the GitHub CLI (gh) with admin access to your repository.

Setup

  1. Install. 
    git clone <your-copy-of-the-template> && cd snowflake-mlops
uv sync --group ml-runtime
  2. Create infrastructure (DEV, STAGE, and PROD databases, warehouses, and compute pools): 
    bash scripts/setup.sh
  3. Load sample data (skip when using your own source tables): 
    uv run python scripts/generate_dataset.py
  4. Run in DEV: 
    uv run python source/pipeline/train_dag.py --deploy --env dev
uv run python source/pipeline/train_dag.py --execute --env dev
  5. Set up CI/CD. The repository IDs form the OIDC subject each service user trusts. 
    # gh api repos/<owner>/<repo> --jq '.id, .owner.id'
GITHUB_OWNER=<owner> GITHUB_OWNER_ID=<owner_id> GITHUB_REPO=<repo> GITHUB_REPO_ID=<repo_id> \
  bash scripts/setup_cicd.sh
    This creates the roles, OIDC service users, network policy, branch protection, and the STAGE and PROD GitHub environments. It is idempotent.
  6. Set repository variables (Settings, Secrets and variables, Actions, Variables):

Bring your own model

Registration, gating, batch scoring, real-time health checks, and monitoring read the model's signature and configuration; they contain no model-specific code. To adopt the template:

  1. Describe the model in config.yml: 
    model:
  name: MY_MODEL
  task_type: binary_classification   # binary_classification | multiclass | regression
  predict_function: predict_proba    # predict for regressors
  id_columns: [CUSTOMER_ID]          # carried through to predictions
  label_column: LABEL
  2. Replace two functions in source/model_training/training.py: build_dataset(session) (returns the Dataset and a pandas frame) and train_model(X_train, y_train) (returns a fitted model). Any model type the Model Registry supports works.
  3. Define your features in source/feature_engineering/feature_views.py.
  4. Set your bar under quality_gate. The shipped thresholds are deliberately low so the synthetic demo passes; replace them before production use.
  5. Pin libraries in the ml-runtime dependency group of pyproject.toml (see Library versions).

Versioning and lineage

ArtifactVersion schemeBehavior
Feature viewfeature_store.view_version (V1, V2, ...)Immutable. Reused when the definition is unchanged (no rebuild). Changing the output columns without bumping the version fails the run with a clear message. Bump it for any change to feature logic, including changes that keep the same columns.
Training Dataset<view_version>_<UTC timestamp>A new point-in-time snapshot per training run, so retraining sees new data.
ModelV1, V2, ... per environmentIncremented on each run; rejected candidates are dropped. PROD receives the same version name as the STAGE candidate it promotes, and its default version is the champion.
ReleaseGit tag prod/<VERSION>-<timestamp>Marks the commit that produced each production version.

Each model version carries a comment such as features:CUSTOMER_RISK_FEATURES$V1 | dataset:MLOPS_FRAUD_DETECTOR_TRAINING_DATA/V1_20261018_235217 | git:6878199, its metrics, the gate decision, and registry lineage to the Dataset. Promotion copies the comment to PROD.

Retention. Every run adds a model version and a Dataset version. After each successful STAGE and PROD deploy, source/utils/retention.py keeps the newest retention.keep_model_versions and retention.keep_dataset_versions per environment. It never removes the default version, a version with an inference service or a model monitor, or a Dataset that a remaining version's lineage references, including PROD versions that point at STAGE Datasets. Preview with --dry-run.

Library versions

Each library is pinned once, in the ml-runtime group of pyproject.toml:

ml-runtime = ["snowflake-ml-python==2.4.0", "xgboost==3.3.0", "scikit-learn==1.8.0"]
Where code runsHow the pins are applied
CI runner and laptopsuv.lock (the same snowflake-ml-python pin is in the project dependencies)
ML Jobs on a compute poolpip_requirements, installed from PyPI through the pypi_access_integration external access integration
Stored procedures on a warehousePACKAGES from the Snowflake Anaconda channel
Model Registry servinglog_model(conda_dependencies=...); the Registry adds snowflake-ml-python at the logging client's version

Every pipeline step checks the installed versions against the pins before it runs and fails on a mismatch.

Without PyPI access, pins are silently ignored

An ML Job that can't reach PyPI keeps the runtime image's preinstalled versions and doesn't fail on its own. In testing, a job pinned to snowflake-ml-python==2.4.0 ran with the image's 1.54.0. setup.sh creates MLOPS_PYPI_ACCESS_INTEGRATION (egress to pypi.org and files.pythonhosted.org) and setup_cicd.sh grants it to MLOPS_STAGE_ROLE; the version check catches any gap. When you bump a pin, choose a version available on both PyPI and the Anaconda channel (SELECT * FROM INFORMATION_SCHEMA.PACKAGES WHERE LANGUAGE = 'python').

Quality gate

A candidate must pass two checks, both evaluated in the EVALUATE step:

  • Metric rules: absolute bars, for example auc_roc: {min: 0.80} or log_loss: {max: 0.4}. Metric names come from model_training/metrics.py for the configured task type.
  • Champion comparison: the default version of the PROD model is scored on the candidate's holdout. The candidate must beat it on champion.metric by at least min_improvement. A small negative margin tolerates noise when retraining on similar data. With no PROD model yet, only the rules apply.
quality_gate:
  metrics:
    auc_roc: {min: 0.80}
    recall: {min: 0.60}
  champion:
    enabled: true
    source_env: prod
    metric: auc_roc
    higher_is_better: true
    min_improvement: -0.01

The STAGE job summary shows the result:

STAGE candidate MLOPS_FRAUD_DETECTOR/V5: quality gate PASSED
Champion comparison: candidate auc_roc=0.5084 beats champion V4 auc_roc=0.5084 (improvement +0.0000, required >= -0.0100)

| Metric           | Candidate (V5) | Champion (V4) | Change         | Gate rule | Result |
| auc_roc (decision)| 0.5084        | 0.5084        | +0.0000 (same) | >= 0.01   | pass   |
| log_loss         | 0.6748         | 0.6748        | +0.0000 (same) |           |        |

Serving

Enable batch, real-time, or both with serving.batch.enabled and serving.realtime.enabled. CI skips the steps for disabled modes, so a batch-only use case never provisions an inference service.

Batch

A scheduled task, <MODEL>_BATCH_INFERENCE, scores serving.batch.input_table (default: the training feature view) with the PROD default version and appends to serving.batch.output_table with MODEL_VERSION, SCORED_AT, and RUN_ID. Because it always uses the default version, it follows promotions and rollbacks automatically.

Real-time

Stale splits are refused

apply_gateway_config.py refuses any split that would drop the live service for the PROD default version. A deploy/gateway-config.yml that predates the last deploy can't take the serving model offline. To move traffic off the default version, run rollback.yml, which changes the default first.

Each PROD version gets its own inference service behind one gateway, which gives clients one stable URL while CI shifts traffic between versions. Traffic weights live in deploy/gateway-config.yml; edit them and merge to main to shift traffic. Whenever a split is applied, every model service that isn't a gateway target is dropped, so only versions taking traffic use compute; the rollback workflow redeploys a dropped version on demand.

Call the endpoint with a programmatic access token. Method names map to paths with dashes (predict_proba becomes /predict-proba):

curl -X POST "https://<gateway-ingress-url>/predict-proba" \
  -H 'Authorization: Snowflake Token="<PAT>"' \
  -H 'Content-Type: application/json' \
  -d '{"dataframe_split": {"index": [0], "columns": ["TOTAL_TXN_COUNT", "..."], "data": [[20, "..."]]}}'

The response is {"data": [[row_index, {"output_feature_0": ..., "output_feature_1": ...}], ...]}. Notebook 06 fetches features from the Feature Store, calls the gateway, and checks the results match ModelVersion.run. The same checks run after every PROD deploy, traffic shift, and rollback (scripts/smoke_test_endpoint.py), and as live tests you can run against PROD:

SNOWFLAKE_DATABASE=SNOW_MLOPS_PROD SNOWFLAKE_WAREHOUSE=SNOW_MLOPS_PROD_WH \
  uv run pytest tests/test_endpoint.py -v
Authentication

Use a PAT. Only the service owner can call the endpoint unless you grant the service role ALL_ENDPOINTS_USAGE; authorization failures return 404. See Deploy models for real-time inference (REST API) and Gateways.

Monitoring

When ENABLE_MODEL_MONITOR is true, deploy-prod creates a model monitor on the PROD default version. Its source is a view over the batch predictions joined to ground truth (monitor.actuals), so it reports performance metrics as well as drift. Rows are identified by id_columns plus RUN_ID, because the append-only history repeats entity keys.

  • Baseline: auto snapshots the promotion-time validation scoring.
  • Drift alert: a Snowflake alert checks drift_metric (default PSI) against drift_threshold on alert_schedule, writes to DRIFT_ALERTS, and optionally emails through a notification integration.

See CREATE MODEL MONITOR.

RoleUsed byAccess

Each service user has a default warehouse (OIDC sessions start without one) and the GITHUB_ACTIONS_POLICY network policy, which uses Snowflake's managed network rule for GitHub Actions runners.

Multi-account setup

Not included in the template

The template promotes between databases in one account. Many organizations instead use a separate account per environment. The steps below describe how to adapt it; they aren't implemented or tested in the repository.

Across accounts, a model is promoted by replicating the database that contains it into the production account, then creating a production model from the replica. Based on Copy models between databases, schemas, and accounts:

  1. In the STAGE account, create a primary replication group for the STAGE database (ACCOUNTADMIN): 
    CREATE REPLICATION GROUP mlops_models_rg
  OBJECT_TYPES = DATABASES
  ALLOWED_DATABASES = SNOW_MLOPS_STAGE
  ALLOWED_ACCOUNTS = myorg.prod_account;
  2. In the PROD account, create the secondary group, refresh it, and optionally schedule refreshes: 
    CREATE REPLICATION GROUP mlops_models_rg AS REPLICA OF myorg.stage_account.mlops_models_rg;
ALTER REPLICATION GROUP mlops_models_rg REFRESH;
ALTER REPLICATION GROUP mlops_models_rg SET REPLICATION_SCHEDULE = '10 MINUTE';
  3. Grant the PROD role access to the replica, including OWNERSHIP on its models (required to copy model files): 
    GRANT USAGE ON DATABASE SNOW_MLOPS_STAGE TO ROLE MLOPS_PROD_ROLE;
GRANT USAGE ON SCHEMA SNOW_MLOPS_STAGE.ML TO ROLE MLOPS_PROD_ROLE;
GRANT OWNERSHIP ON ALL MODELS IN SCHEMA SNOW_MLOPS_STAGE.ML TO ROLE MLOPS_PROD_ROLE;
  4. Promote from the replica in the PROD account. The production model is a separate object; each new version must be added explicitly: 
    CREATE MODEL SNOW_MLOPS_PROD.ML.MLOPS_FRAUD_DETECTOR WITH VERSION V5
  FROM MODEL SNOW_MLOPS_STAGE.ML.MLOPS_FRAUD_DETECTOR VERSION V5;
-- later versions
ALTER MODEL SNOW_MLOPS_PROD.ML.MLOPS_FRAUD_DETECTOR ADD VERSION V6
  FROM MODEL SNOW_MLOPS_STAGE.ML.MLOPS_FRAUD_DETECTOR VERSION V6;

To wire this into the template:

  • Add a promotion script (for example deploy/promote_multi_account.py) with a promote(version) that refreshes the replication group, waits for the candidate version to appear in the replica, and runs the statements above. Use it from deploy-prod in place of deploy/promote.py.
  • Run setup.sh and setup_cicd.sh in each account, with a separate SNOWFLAKE_ACCOUNT per GitHub environment. OIDC users are per account.
  • The champion comparison reads the PROD model from STAGE. Across accounts, either replicate the PROD database back to STAGE or disable quality_gate.champion and compare in deploy-prod instead.
  • Source data, feature views, services, the gateway, and monitors must exist in the PROD account. deploy-prod already registers PROD feature views before batch validation.
  • Secondary databases are read-only, and replication refresh adds latency between gating and promotion.
