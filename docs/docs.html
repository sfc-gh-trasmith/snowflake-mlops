MLOps on Snowflake

GuideOpen-source template

Build, validate, promote, serve, and monitor machine learning models across development, staging, and production environments, with Git as the system of record and Snowflake as the platform where data, features, models, and inference live together.

MLOps is the set of practices that makes machine learning repeatable and safe in production: every model is traceable to the code and data that produced it, every promotion passes automated checks and a human approval, and production models are monitored and can be rolled back. On Snowflake, these practices run where the data already is: feature pipelines, training jobs, the model registry, inference, and monitoring are Snowflake objects, governed by the same roles and policies as your data.

This guide has two parts:

  • MLOps on Snowflake: the lifecycle, a reference architecture for dev/stage/prod with a Git workflow, and how responsibilities split between personas.
  • The MLOps template: an open-source project that implements that architecture end to end, with an in-depth look at how it orchestrates training, gating, promotion, serving, and monitoring, and how to adopt it.

The ML lifecycle on Snowflake

Each stage of the lifecycle maps to a Snowflake ML capability. Because they share one platform, the handoffs between stages (features to training, training to registry, registry to inference, inference to monitoring) are object references rather than file exports.

Reference architecture: environments and Git workflow

A common, robust pattern separates three environments, each with its own database, warehouse, and compute pool, and drives every change through Git:

DEV

Data scientists explore data, iterate on features and models in notebooks, and run the pipeline on demand. Nothing here serves traffic.

STAGE

Every merge to main retrains the model from the committed code, gates it on quality and against the production champion, and validates batch and monitoring end to end.

PROD

After a human approves, the gated version is promoted, scheduled batch scoring and real-time endpoints are updated, monitoring is attached, and the release is tagged in Git.

Design principles

  • Git is the source of truth. Feature logic, training code, configuration, and real-time traffic weights are all committed. Environments are rebuilt from the repository, not edited by hand.
  • Train where you deploy from. The candidate promoted to PROD is the exact model version trained and validated in STAGE; promotion copies that version rather than retraining it.
  • Automated checks, human decisions. Code quality, data checks, metric thresholds, and champion comparison are automated. Promotion to production requires an explicit approval.
  • Everything is versioned and traceable. A production model version links back to its training dataset version, feature view version, experiment run, and Git commit.
  • Least privilege per environment. CI uses separate roles for STAGE and PROD and authenticates with OIDC, so there are no long-lived credentials in the repository.

Part 2

The MLOps template

The snowflake-mlops template is an open-source repository that implements the reference architecture above with GitHub Actions and Snowflake ML. It ships with a working example (a fraud classifier on synthetic data) and is model-agnostic: you swap in your own features and model, and the platform pieces (versioning, gating, promotion, serving, monitoring, rollback) keep working.

Pipeline

A Snowflake task graph: data checks and feature engineering, training and registration, evaluation and gating. Each step runs on a warehouse or a compute pool, chosen in config.

Promotion

Code-driven (merge to main) and data-driven (weekly retrain). PROD requires approval and receives the exact STAGE version.

Serving

Batch, real-time, or both. A scheduled scoring task, and per-version inference services behind a gateway with canary weights in Git.

Operations

Model monitor with ground truth, drift alerts, one-click and automatic rollback, a REST smoke test, release tags, and a job summary comparing every candidate with the champion.

Scope

The template targets a single Snowflake account with one database per environment. For separate accounts per environment, see Multi-account setup.

Template architecture

GitHub Actions orchestrates releases; all ML work runs in Snowflake. CI authenticates to Snowflake with OIDC workload identity, using a STAGE role for training and validation and a PROD role for promotion and serving. Source data lives in PROD and is read by every environment; each environment writes its own feature views, datasets, models, and results.

Training pipeline

The training pipeline is a Snowflake task graph named MLOPS_DEMO_TASK, deployed and run by source/pipeline/train_dag.py. Each step is a package under source/ exposing run(session) -> dict. At deploy time the step code and configuration are zipped and staged; each step then runs either as an ML Job on a compute pool or as a stored procedure on a warehouse, according to pipeline_steps in config.yml. Steps hand results to each other through the PIPELINE_RESULTS table.

StepDefault computeWhat it does
FEATURE_ENGCompute pool (ML Job)Runs data_checks on source tables, then registers the entities and feature views. A feature view version is immutable: if it exists with the same schema it is reused; if the columns changed without a version bump, the step fails.
TRAIN_MODELCompute pool (ML Job)Generates a new Dataset version from the feature view, trains on a grouped split, computes task-appropriate metrics, scores the PROD champion on the same holdout, and logs a new model version with lineage, metrics, and task= for ML Observability.
EVALUATEWarehouse (stored procedure)Applies quality_gate.metrics rules and the champion comparison. On pass, records the decision on the version; on fail, drops the version and fails the task.

Run the pipeline on demand from your machine:

uv run python source/pipeline/train_dag.py --deploy --env dev
uv run python source/pipeline/train_dag.py --execute --env dev

Promotion workflow

The template supports two promotion paths. Both end with a human approval before anything changes in PROD.

Code-driven

A merge to main runs deploy.yml: STAGE trains and gates the new code, then PROD waits for approval.

Data-driven

scheduled-retrain.yml retrains weekly on fresh data in STAGE and opens a GitHub issue. A reviewer promotes the candidate with deploy.yml (promote_only).

deploy-stage

  1. Deploy the training task graph to STAGE and trigger it.
  2. Wait for completion; read this run's evaluation from PIPELINE_RESULTS.
  3. Write the job summary: every metric for the candidate and the PROD champion side by side, the change, the decision metric, per-rule results, and lineage. It is written even if the pipeline fails, so rejections are reported.
  4. If batch serving is enabled, score with the candidate and validate the outputs.
  5. If monitoring is enabled, create the monitor and drift alert, verify them, then drop them.
  6. Retention: prune STAGE model and Dataset versions beyond the newest N (see Versioning and lineage).

deploy-prod (after approval)

  1. Capture the current PROD default version and gateway split, for automatic rollback.
  2. Promote: copy the gated version into the PROD registry with CREATE MODEL ... FROM MODEL or ALTER MODEL ... ADD VERSION ... FROM MODEL, copy the lineage comment, and set it as the default version. Re-running is safe: an identical version already in PROD is kept.
  3. Batch: register PROD feature views, validate scoring with the promoted version, and deploy the scheduled scoring task.
  4. Real-time: create <MODEL>_SERVICE_<VERSION>, health-check it (valid outputs, parity with warehouse scoring within 1e-4, agreement with the incumbent), then route canary_weight% of gateway traffic to it. The first deploy creates the gateway with 100% to the new version. Applying the split drops every model service that isn't a gateway target; a service that fails its health check is dropped before it takes traffic.
  5. REST smoke test: real HTTPS calls to the gateway and to each service behind it, authenticated with a one-day PAT that the job issues for its own service user and removes afterwards. Each response must have one valid prediction per row and match warehouse scoring of the same version.
  6. Commit the new weights to gateway-config.yml.
  7. Create or update the PROD model monitor and drift alert.
  8. Retention: prune old PROD model versions.
  9. Tag the release as prod/<VERSION>-<timestamp>.
Automatic rollback

If any step after promotion fails (service, health check, gateway, smoke test, or monitor), deploy-prod restores the captured default version and gateway split, which also drops the failed version's service. Batch scoring follows the default version, so it is restored too. On the very first deployment there is nothing to restore, and the job just fails.

Persona journeys

Data scientist: ship a model improvement

  1. Explore in DEV. Use notebooks 01–03 to explore source data, prototype features, and train locally against Snowflake data.
  2. Change the code. On a feature branch, edit feature_views.py and training.py. If you changed feature columns or logic, bump feature_store.view_version.
  3. Run the pipeline in DEV. train_dag.py --deploy --execute --env dev runs the same task graph CI uses, so problems show up before review.
  4. Open a pull request. Lint and unit tests run; a teammate reviews.
  5. Read the STAGE job summary after merge: your candidate's metrics next to the PROD champion's, scored on the same holdout.
  6. Hand off for approval. If the gate passed, the approver promotes it; if not, the summary lists the failed rules.

ML engineer: operate the platform

  1. Provision. Run setup.sh and setup_cicd.sh; set the GitHub variables and environments.
  2. Choose compute and serving. Set pipeline_steps.*.compute, serving.batch, and serving.realtime in config.yml.
  3. Set the bar with the data scientist. Agree on quality_gate.metrics and the champion metric and margin.
  4. Manage the canary. After deploy-prod, raise the new version's weight in gateway-config.yml through a pull request; traffic-shift.yml applies it and drops services you remove.
  5. Watch production. Review model monitor dashboards and DRIFT_ALERTS; run rollback.yml to revert to a previous version.

Get started

Prerequisites

  • A Snowflake account and a role that can create databases, warehouses, compute pools, roles, and users (the setup scripts use ACCOUNTADMIN).
  • Python 3.11 or 3.12, uv, the Snowflake CLI (snow) with a configured connection, and the GitHub CLI (gh) with admin access to your repository.

Setup

  1. Install. 
    git clone <your-copy-of-the-template> && cd snowflake-mlops

Bring your own model

Registration, gating, batch scoring, real-time health checks, and monitoring read the model's signature and configuration; they contain no model-specific code. To adopt the template:

  1. Describe the model in config.yml: 
    model:
  name: MY_MODEL
  task_type: binary_classification   # binary_classification | multiclass | regression
  predict_function: predict_proba    # predict for regressors
  id_columns: [CUSTOMER_ID]          # carried through to predictions
  label_column: LABEL
  2. Replace two functions in source/model_training/training.py: build_dataset(session) (returns the Dataset and a pandas frame) and train_model(X_train, y_train) (returns a fitted model). Any model type the Model Registry supports works.
  3. Define your features in source/feature_engineering/feature_views.py.
  4. Set your bar under quality_gate. The shipped thresholds are deliberately low so the synthetic demo passes; replace them before production use.
  5. Pin libraries in the ml-runtime dependency group of pyproject.toml (see Library versions).

Versioning and lineage

ArtifactVersion schemeBehavior
Feature viewfeature_store.view_version (V1, V2, ...)Immutable. Reused when the definition is unchanged (no rebuild). Changing the output columns without bumping the version fails the run with a clear message. Bump it for any change to feature logic, including changes that keep the same columns.
Training Dataset<view_version>_<UTC timestamp>A new point-in-time snapshot per training run, so retraining sees new data.
ModelV1, V2, ... per environmentIncremented on each run; rejected candidates are dropped. PROD receives the same version name as the STAGE candidate it promotes, and its default version is the champion.
ReleaseGit tag prod/<VERSION>-<timestamp>Marks the commit that produced each production version.

Each model version carries a comment such as features:CUSTOMER_RISK_FEATURES$V1 | dataset:MLOPS_FRAUD_DETECTOR_TRAINING_DATA/V1_20261018_235217 | git:6878199, its metrics, the gate decision, and registry lineage to the Dataset. Promotion copies the comment to PROD.

Retention. Every run adds a model version and a Dataset version. After each successful STAGE and PROD deploy, source/utils/retention.py keeps the newest retention.keep_model_versions and retention.keep_dataset_versions per environment. It never removes the default version, a version with an inference service or a model monitor, or a Dataset that a remaining version's lineage references, including PROD versions that point at STAGE Datasets. Preview with --dry-run.

Library versions

Each library is pinned once, in the ml-runtime group of pyproject.toml:

ml-runtime = ["snowflake-ml-python==2.4.0", "xgboost==3.3.0", "scikit-learn==1.8.0"]
Where code runsHow the pins are applied
CI runner and laptopsuv.lock (the same snowflake-ml-python pin is in the project dependencies)
ML Jobs on a compute poolpip_requirements, installed from PyPI through the pypi_access_integration external access integration
Stored procedures on a warehousePACKAGES from the Snowflake Anaconda channel
Model Registry servinglog_model(conda_dependencies=...); the Registry adds snowflake-ml-python at the logging client's version

Every pipeline step checks the installed versions against the pins before it runs and fails on a mismatch.

Without PyPI access, pins are silently ignored

An ML Job that can't reach PyPI keeps the runtime image's preinstalled versions and doesn't fail on its own. In testing, a job pinned to snowflake-ml-python==2.4.0 ran with the image's 1.54.0. setup.sh creates MLOPS_PYPI_ACCESS_INTEGRATION (egress to pypi.org and files.pythonhosted.org) and setup_cicd.sh grants it to MLOPS_STAGE_ROLE; the version check catches any gap. When you bump a pin, choose a version available on both PyPI and the Anaconda channel (SELECT * FROM INFORMATION_SCHEMA.PACKAGES WHERE LANGUAGE = 'python').

Quality gate

A candidate must pass two checks, both evaluated in the EVALUATE step:

  • Metric rules: absolute bars, for example auc_roc: {min: 0.80} or log_loss: {max: 0.4}. Metric names come from model_training/metrics.py for the configured task type.
  • Champion comparison: the default version of the PROD model is scored on the candidate's holdout. The candidate must beat it on champion.metric by at least min_improvement. A small negative margin tolerates noise when retraining on similar data. With no PROD model yet, only the rules apply.
quality_gate:
  metrics:
    auc_roc: {min: 0.80}
    recall: {min: 0.60}
  champion:
    enabled: true
    source_env: prod
    metric: auc_roc
    higher_is_better: true
    min_improvement: -0.01

The STAGE job summary shows the result:

STAGE candidate MLOPS_FRAUD_DETECTOR/V5: quality gate PASSED
Champion comparison: candidate auc_roc=0.5084 beats champion V4 auc_roc=0.5084 (improvement +0.0000, required >= -0.0100)

Serving

Enable batch, real-time, or both with serving.batch.enabled and serving.realtime.enabled. CI skips the steps for disabled modes, so a batch-only use case never provisions an inference service.

Batch

A scheduled task, <MODEL>_BATCH_INFERENCE, scores serving.batch.input_table (default: the training feature view) with the PROD default version and appends to serving.batch.output_table with MODEL_VERSION, SCORED_AT, and RUN_ID. Because it always uses the default version, it follows promotions and rollbacks automatically.

Real-time

Each PROD version gets its own inference service behind one gateway, which gives clients one stable URL while CI shifts traffic between versions. Traffic weights live in gateway-config.yml; edit them and merge to main to shift traffic. Whenever a split is applied, every model service that isn't a gateway target is dropped, so only versions taking traffic use compute; the rollback workflow redeploys a dropped version on demand.

Call the endpoint with a programmatic access token. Method names map to paths with dashes (predict_proba becomes /predict-proba):

curl -X POST "https://<gateway-ingress-url>/predict-proba" \
  -H 'Authorization: Snowflake Token="<PAT>"' \
  -H 'Content-Type: application/json' \
  -d '{"dataframe_split": {"index": [0], "columns": ["TOTAL_TXN_COUNT", "..."], "data": [[20, "..."]]}}'

The response is {"data": [[row_index, {"output_feature_0": ..., "output_feature_1": ...}], ...]}. Notebook 06 fetches features from the Feature Store, calls the gateway, and checks the results match ModelVersion.run. The same checks run after every PROD deploy, traffic shift, and rollback (scripts/smoke_test_endpoint.py), and as live tests you can run against PROD:

SNOWFLAKE_DATABASE=SNOW_MLOPS_PROD SNOWFLAKE_WAREHOUSE=SNOW_MLOPS_PROD_WH \
  uv run pytest tests/test_endpoint.py -v
Authentication

Use a PAT. Only the service owner can call the endpoint unless you grant the service role ALL_ENDPOINTS_USAGE; authorization failures return 404. See Deploy models for real-time inference (REST API) and Gateways.

Monitoring

When ENABLE_MODEL_MONITOR is true, deploy-prod creates a model monitor on the PROD default version. Its source is a view over the batch predictions joined to ground truth (monitor.actuals), so it reports performance metrics as well as drift. Rows are identified by id_columns plus RUN_ID, because the append-only history repeats entity keys.

  • Baseline: auto snapshots the promotion-time validation scoring.
  • Drift alert: a Snowflake alert checks drift_metric (default PSI) against drift_threshold on alert_schedule, writes to DRIFT_ALERTS, and optionally emails through a notification integration.

See CREATE MODEL MONITOR.

Multi-account setup

Not included in the template

The template promotes between databases in one account. Many organizations instead use a separate account per environment. The steps below describe how to adapt it; they aren't implemented or tested in the repository.

Across accounts, a model is promoted by replicating the database that contains it into the production account, then creating a production model from the replica. Based on Copy models between databases, schemas, and accounts:

  1. In the STAGE account, create a primary replication group for the STAGE database (ACCOUNTADMIN): 
    CREATE REPLICATION GROUP mlops_models_rg
  OBJECT_TYPES = DATABASES
  ALLOWED_DATABASES = SNOW_MLOPS_STAGE
  ALLOWED_ACCOUNTS = myorg.prod_account;
  2. In the PROD account, create the secondary group, refresh it, and optionally schedule refreshes: 
    CREATE REPLICATION GROUP mlops_models_rg AS REPLICA OF myorg.stage_account.mlops_models_rg;
ALTER REPLICATION GROUP mlops_models_rg REFRESH;
ALTER REPLICATION GROUP mlops_models_rg SET REPLICATION_SCHEDULE = '10 MINUTE';
  3. Grant the PROD role access to the replica, including OWNERSHIP on its models (required to copy model files): 
    GRANT USAGE ON DATABASE SNOW_MLOPS_STAGE TO ROLE MLOPS_PROD_ROLE;
GRANT USAGE ON SCHEMA SNOW_MLOPS_STAGE.ML TO ROLE MLOPS_PROD_ROLE;
GRANT OWNERSHIP ON ALL MODELS IN SCHEMA SNOW_MLOPS_STAGE.ML TO ROLE MLOPS_PROD_ROLE;
  4. Promote from the replica in the PROD account. The production model is a separate object; each new version must be added explicitly: 
    CREATE MODEL SNOW_MLOPS_PROD.ML.MLOPS_FRAUD_DETECTOR WITH VERSION V5
  FROM MODEL SNOW_MLOPS_STAGE.ML.MLOPS_FRAUD_DETECTOR VERSION V5;
-- later versions
ALTER MODEL SNOW_MLOPS_PROD.ML.MLOPS_FRAUD_DETECTOR ADD VERSION V6
  FROM MODEL SNOW_MLOPS_STAGE.ML.MLOPS_FRAUD_DETECTOR VERSION V6;

To wire this into the template:

  • Add a promotion script (for example deploy/promote_multi_account.py) with a promote(version) that refreshes the replication group, waits for the candidate version to appear in the replica, and runs the statements above. Use it from deploy-prod in place of deploy/promote.py.
  • Run setup.sh and setup_cicd.sh in each account, with a separate SNOWFLAKE_ACCOUNT per GitHub environment. OIDC users are per account.
  • The champion comparison reads the PROD model from STAGE. Across accounts, either replicate the PROD database back to STAGE or disable quality_gate.champion and compare in deploy-prod instead.
  • Source data, feature views, services, the gateway, and monitors must exist in the PROD account. deploy-prod already registers PROD feature views before batch validation.
  • Secondary databases are read-only, and replication refresh adds latency between gating and promotion.
