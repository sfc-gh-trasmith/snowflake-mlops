MLOps on Snowflake

End-to-End Machine Learning Operations Framework

Overview

What is MLOps?

MLOps (Machine Learning Operations) is the set of practices that combines ML system development with reliable deployment and ongoing operations. It bridges the gap between data science experimentation and production-grade ML systems by standardizing how models are trained, validated, deployed, monitored, and retrained over time.

In practice, MLOps solves several critical challenges that ML teams face when moving from notebook prototypes to production:

  • Reproducibility — every training run is tracked with parameters, metrics, and data lineage
  • Automation — pipelines run on schedule or on code change without manual intervention
  • Quality gates — models must pass metric thresholds before reaching production
  • Governance — human approval required for production deployments, with full audit trail
  • Observability — drift detection and performance monitoring catch degradation early

End-to-End ML on Snowflake

Snowflake ML provides an integrated set of capabilities for the full machine learning lifecycle — from feature engineering through model serving and monitoring — all running on top of your governed data. Key platform capabilities this framework uses:

About This Framework

This is an open-source, production-ready template for building end-to-end ML pipelines on Snowflake. It provides starter code that data science teams can plug their own model logic into, while giving ML engineering teams a standardized process for training, validating, deploying, and monitoring models.

Extensible by design The framework is intentionally modular. Swap in your own training algorithm, add new feature engineering steps, adjust quality gate thresholds, or extend the CI/CD workflows — the surrounding infrastructure (orchestration, versioning, deployment, monitoring) stays the same. Use it as a bootstrap for your MLOps workflows, or as a baseline to extend with Cortex Code for agentic ML.

For data science teams: replace the training function, update feature engineering, adjust thresholds. Everything else (CI/CD, versioning, deployment, monitoring) works automatically.

For ML engineering teams: standardized pipeline structure, automated CI/CD with approval gates, environment isolation (DEV → STAGE → PROD), reproducible deployments, and one-click rollback.

One-Time Setup

Before the CI pipeline can run, three setup steps must be completed once by an account admin:

1. Infrastructure bash scripts/setup.sh Creates DEV / STAGE / PROD databases, schemas, warehouses (MEDIUM, auto-suspend 120s), compute pools (CPU_X64_M, 1–3 nodes), and three general-purpose stages per environment: ML_ARTIFACTS, DAG_STAGE, JOB_STAGE. Task DAG Orchestration

The pipeline is defined using the Python SDK (snowflake.core.task.dagv1) which provides a programmatic interface for creating and managing Snowflake Tasks. This approach is preferred over raw SQL because it's easier to modify, test, and integrate with CI/CD.

Key insight: The ML logic does not live in the DAG file. Each step is a package under source/ whose logic module exposes one function, run(session). The DAG builds a thin wrapper around it whose only job is to import the step module, call run(), and return JSON. For SPCS, that wrapper is an @remote ML Job; cloudpickle serializes only the wrapper, so source.zip is mounted into the container explicitly via imports=. For warehouse, the wrapper is an anonymous stored procedure whose IMPORTS clause points at the same staged source.zip.
The same config ships with the code source.zip contains config.py and configs/config.yml, so step modules import settings at module level exactly as they do locally (from config import MODEL_NAME, TRAINING_PARAMS). config.py reads the YAML through the module loader, which works whether it is on disk or inside a zip import. The one thing that differs per run is the target environment: each wrapper sets SNOWFLAKE_DATABASE / SCHEMA / WAREHOUSE / COMPUTE_POOL from resolve_env_config(env) before importing the step. This matters on SPCS, where the container sets its own SNOWFLAKE_DATABASE to the ML Job stage's database.
PIPELINE_STAGE vs setup.sh stages scripts/setup.sh creates three stages for general use: ML_ARTIFACTS, DAG_STAGE, and JOB_STAGE. The pipeline uses a separate stage called PIPELINE_STAGE, which is created automatically by train_dag.py --deploy at CI time. You do not need to create PIPELINE_STAGE manually — it is provisioned idempotently on every deploy run.

Configurable Compute Per Step

Each pipeline step independently runs on either a warehouse WH or a compute pool SPCS, configured in source/configs/config.yml:

pipeline_steps:
  feature_eng:
    compute: spcs        # "warehouse" or "spcs"
  train_model:
    compute: spcs
  evaluate:
    compute: warehouse   # lightweight eval runs on warehouse
ModeWhen to UseImplementation
SPCSGPU training, arbitrary pip packages, long-running compute@remote ML Job on the compute pool, source.zip mounted via imports=
WHSQL-heavy, lightweight Python, cost-sensitive, no container cold startAnonymous stored procedure with IMPORTS=('@PIPELINE_STAGE/source.zip')
Switching compute is a config change, never a code change Both modes call the same run(session) function in the step's logic module. Because the step contract is uniform, the two wrappers in train_dag.py are generic — adding a step requires no new dispatch code, only an entry in STEPS. All-warehouse mode is fully supported for every step, including training.

DAG Definition Pattern

The DAG is built generically from STEPS. _task_def() reads each step's configured compute and returns either an @remote ML Job or an anonymous stored procedure body:

from snowflake.core.task.dagv1 import DAG, DAGOperation, DAGTask
from config import resolve_env_config, step_compute

cfg = resolve_env_config(env)   # target DB / schema / WH / pool for this env

def _task_def(task_name, cfg, ...):
    mode = step_compute(STEPS[task_name]["config_key"])
    if mode == "spcs":
        return _remote_def(task_name, cfg, job_stage, source_zip)   # ML Job
    return _sproc_def(task_name, cfg, imports, packages)           # anonymous sproc

with DAG(DAG_NAME, warehouse=wh, stage_location=pipeline_stage) as dag:
    tasks = {
        name: DAGTask(name, definition=_task_def(name, cfg, ...), warehouse=wh)
        for name in STEP_ORDER
    }
    for upstream, downstream in zip(STEP_ORDER, STEP_ORDER[1:]):
        tasks[upstream] >> tasks[downstream]

# Deploy to Snowflake
schema_ref = root.databases[db].schemas[schema]
DAGOperation(schema_ref).deploy(dag, mode=CreateMode.or_replace)

Each wrapper body is the same few lines regardless of compute mode:

os.environ.update(env)   # pin target DB / schema / WH
step = importlib.import_module(module)   # e.g. "model_training.training"
return json.dumps(step.run(session))

Task Naming Convention

The Python SDK prefixes child task names with the DAG name:

  • Root: MLOPS_DEMO_TASK
  • Children: MLOPS_DEMO_TASK$FEATURE_ENG, MLOPS_DEMO_TASK$TRAIN_MODEL, MLOPS_DEMO_TASK$EVALUATE

Running a Single Step

Each step package ships an entrypoint.py that calls the same run(session) the DAG invokes, so local behavior matches the pipeline exactly. The target environment comes from SNOWFLAKE_DATABASE / SNOWFLAKE_SCHEMA / SNOWFLAKE_WAREHOUSE (default: DEV):

uv run python source/feature_engineering/entrypoint.py

Feature Store

Data Checks

The FEATURE_ENG step first runs source/feature_engineering/data_checks.py against the source database/schema, using the data_checks: block in config. Each table key supports min_rows, max_null_pct ({column: pct}), and freshness_column + max_age_hours. All rules are optional; the step raises listing every failure, so bad upstream data stops the pipeline before features are built.

Features are managed via Snowflake's native Feature Store with Dynamic Tables for automatic refresh. The feature engineering step registers entities and feature views, then materializes 5000 rows of customer risk features.

Which feature view is used in training? Both feature views are registered by source/feature_engineering/feature_views.py, which the FEATURE_ENG step calls via register_feature_views(session=session) — the single implementation for both compute modes. The pipeline currently trains on CUSTOMER_RISK_FEATURES only. TRANSACTION_CONTEXT_FEATURES is registered and kept fresh, but not yet wired into the training spine. To include it: change build_dataset(session) in source/model_training/training.py to add the TRANSACTION entity to the spine and join both feature views via fs.generate_dataset(..., features=[cust_fv, txn_fv], ...).

Refresh Strategy

Both feature views use configurable refresh intervals, set in source/configs/config.yml:

feature_store:
  view_name: CUSTOMER_RISK_FEATURES
  view_version: V1              # Bump when feature SQL changes
  customer_features_refresh: "1 hour"
  transaction_features_refresh: "1 hour"

Dynamic Tables automatically refresh on this cadence, ensuring features are fresh without manual intervention.

Model Training

Training logic lives in source/model_training/training.py as a single run(session) function. When the step is configured for spcs, the DAG wraps it in an ML Job on a compute pool using the @remote decorator from snowflake.ml.jobs; when configured for warehouse, the same function runs inside an anonymous stored procedure. The step itself is identical in both cases.

What You Replace

Two example functions in training.py are the customization points:

  • build_dataset(session) — builds the training Dataset from the Feature Store
  • train_model(X_train, y_train) — fits and returns the model

Everything else (holdout split, metrics, champion scoring, registration) is generic and driven by the model: contract in config:

model:
  name: MLOPS_FRAUD_DETECTOR
  task_type: binary_classification   # binary_classification | multiclass | regression
  predict_function: predict_proba     # predict_proba for classifiers, predict for regressors
  id_columns: [CUSTOMER_ID]           # carried through to predictions
  label_column: IS_FRAUD

Metrics come from source/model_training/metrics.py per task type:

ML Runtime Dependency Management

Training and serving dependencies are pinned in pyproject.toml under the [dependency-groups] ml-runtime group:

[dependency-groups]
ml-runtime = ["xgboost==3.3.0", "scikit-learn==1.8.0"]

config.py reads this group at import time via tomllib, producing ML_RUNTIME_DEPS. This single source of truth feeds both:

  • Training on SPCS (ML Job): pip_requirements=ML_RUNTIME_DEPS + ["snowflake-ml-python"]
  • Training on a warehouse (stored procedure): PACKAGES=(... + ML_RUNTIME_DEPS) from the Snowflake Anaconda channel
  • Serving (Model Registry): conda_dependencies=ML_RUNTIME_DEPS
Pins match the ML Job runtime image SPCS containers have no internet access by default. The pins are set to the versions already preinstalled in the ML Job runtime image (scikit-learn 1.8.0, xgboost 3.3.0 on Python 3.12), so pip finds them already satisfied and never needs PyPI. Both versions are also published in the Snowflake Anaconda channel, so warehouse training and Registry serving resolve the same versions. Installing a version the image doesn't ship would require an external access integration to PyPI on the ML Job.

To update versions: check the runtime image's versions, edit pyproject.toml, run uv lock, commit. Use uv sync --group ml-runtime for local dev parity.

Dataset Versioning

The training dataset version is tied to the Feature View version:

The Dataset is named <MODEL_NAME>_TRAINING_DATA (e.g. MLOPS_FRAUD_DETECTOR_TRAINING_DATA) and its version equals the Feature View version (feature_store.view_version, e.g. V1).

  • Same FV version (reruns): Reuses existing dataset — fast, no regeneration
  • New FV version (schema change): Creates new dataset version automatically
  • Lineage: Model V3 → Dataset V1 → Feature View V1 (traceable end-to-end). The model is logged with sample_input_data derived from the Dataset, which records the model→Dataset link.

Step Wrapper Pattern

The DAG builds this wrapper around the training step when its compute is spcs. Note that the wrapper carries no ML logic — it only pins the environment, imports the step, and calls it:

@remote(
    pool_name,
    stage_name="@DB.SCHEMA.PIPELINE_STAGE",
    pip_requirements=ML_RUNTIME_DEPS + ["snowflake-ml-python", "pyyaml"],
    imports=[str(source_zip)],   # step packages + config.py + configs/config.yml
    name="TRAIN_MODEL",          # readable ML Job name
)
def run_step() -> str:
    import importlib
    import json
    import os
    from snowflake.snowpark import Session

    os.environ.update(env)       # SNOWFLAKE_DATABASE / SCHEMA / WAREHOUSE / COMPUTE_POOL
    session = Session.builder.getOrCreate()
    session.sql(f"USE WAREHOUSE {env['SNOWFLAKE_WAREHOUSE']}").collect()

    mod = importlib.import_module("model_training.training")
    return json.dumps(mod.run(session))
Important: cloudpickle Serialization Rules

All imports MUST be inside the @remote function body. Module references from outer scope may not serialize correctly. Closure variables (strings, dicts) are captured fine — which is how the target environment reaches the container. Step packages are not pickled at all; they are mounted into the container via imports=.

Training Details

  • Algorithm (example): XGBoost (XGBClassifier)
  • Validation: single grouped holdout (1 of 5 folds, ~20%), grouped by model.id_columns[0] so no entity appears in both train and test. StratifiedGroupKFold for classification, GroupKFold for regression.
  • Champion scoring: the default version in quality_gate.champion.source_env (PROD) is scored on the same holdout via ModelVersion.run(). If there is no champion or it can't score the holdout, the result records a reason and comparison is skipped.
  • Class imbalance: scale_pos_weight=33 (~3% fraud rate)
  • Hyperparameters: from training_params in source/configs/config.yml (n_estimators: 100, max_depth: 6, learning_rate: 0.1)
  • Registration: in this step, to the target environment's Model Registry (no model files are staged)
  • Results written to: PIPELINE_RESULTS (STEP='training': model version, metrics, champion)

SQL for Results Table

-- PARSE_JSON() not allowed in VALUES clause; use INSERT...SELECT
INSERT INTO DB.SCHEMA.PIPELINE_RESULTS (STEP, STATUS, RESULT, CREATED_AT)
SELECT 'training', 'SUCCESS', PARSE_JSON('{"metrics": {...}}'), CURRENT_TIMESTAMP()

Model Registry

The training step registers the candidate directly in the target environment's Model Registry with auto-incremented versioning. The EVALUATE step then keeps or removes it based on the quality gate. CI does not register models.

Registration Flow

  1. Query existing versions and auto-increment: V11 → V12
  2. Log the model with ExperimentTracking.log_model (when experiment.enabled) or Registry.log_model
  3. Pass sample_input_data = a Snowpark DataFrame from the training Dataset (model→Dataset lineage), metrics=..., and conda_dependencies=ML_RUNTIME_DEPS
  4. EVALUATE runs the gate: pass keeps the version; fail drops it
  5. The version becomes DEFAULT in PROD when promoted by deploy-prod
Conda Version Pinning

The conda_dependencies must reference versions available in Snowflake's Anaconda channel. Pin to a specific version (e.g., xgboost==3.3.0) rather than relying on automatic resolution which may pick an unavailable version.

Quality Gate Thresholds

Template defaults are intentionally low The auc_roc, precision, and recall minimums under quality_gate.metrics are all set to 0.01 in the template so the pipeline succeeds end-to-end with synthetic data out of the box. Set these to meaningful values before using this template in production.
MetricTemplate DefaultSuggested Production ValuePurpose
AUC-ROC0.01≥ 0.85Discriminative power
Precision0.01≥ 0.70False positive control
Recall0.01≥ 0.60Fraud detection coverage

The gate runs in the EVALUATE step (source/evaluate/evaluation.py + gate.py) and is configured under quality_gate: in source/configs/config.yml:

quality_gate:
  metrics:                 # {metric: {min: x} | {max: x}}; names from metrics.py
    auc_roc: {min: 0.01}
    precision: {min: 0.01}
    recall: {min: 0.01}
  champion:
    enabled: true
    source_env: prod       # champion = default version in this env
    metric: auc_roc
    higher_is_better: true
    min_improvement: -0.01 # small negative value tolerates noise
  • Absolute rules: every metric in quality_gate.metrics must meet its min / max.
  • Champion comparison: the candidate must beat the PROD default version, scored on the same holdout, by at least min_improvement on champion.metric. If there is no champion or it can't score, the comparison is skipped (passes) with a reason.
  • On pass: set_metric('quality_gate', 'PASSED') and champion_comparison are stored on the version.
  • On fail: the candidate version is dropped from the registry (DROP MODEL if it was the only version), an evaluation row with gate_failures is written to PIPELINE_RESULTS, and the step raises so the DAG and CI fail.

In CI, source/utils/read_candidate.py reads the evaluation result exported by wait_for_task.py, writes a Job Summary with candidate vs champion metrics and the gate rules, emits model_version to GITHUB_OUTPUT, and exits 1 if the gate failed.

Models are registered with target_platforms=["WAREHOUSE", "SNOWPARK_CONTAINER_SERVICES"]. This tells Snowflake to prepare the model for both serving modes:

It runs on a warehouse (no SPCS service needed) and appends predictions to serving.batch.output_table (default BATCH_PREDICTIONS). Enable or disable it with serving.batch.enabled.

Validation Checks

  • No NULLs: If any output is NULL, the model failed to score that row (exit code 1)
  • Probability sanity (classifiers): each probability in [0, 1] and each row summing to 1 within 0.01

Checks come from source/serving/signature.py (validate_outputs / validate_outputs_sql), which also casts inputs to the model signature for Snowpark and pandas and derives output_columns. There are no hardcoded feature lists.

How It Works Under the Hood

When the model was registered with conda_dependencies=ML_RUNTIME_DEPS, Snowflake created a vectorized Python UDF backed by the serialized model. mv.run() invokes that UDF over the input DataFrame — all computation stays inside the warehouse, no data leaves Snowflake, no SPCS service needed.

Health Check

Before shifting traffic, health_check_rows real rows from the batch input table are sent directly to the new service (bypassing the gateway):

  1. Valid outputs for the task type (no NULLs; probabilities valid for classifiers)
  2. Parity: service output matches warehouse mv.run() for the same version within 1e-4
  3. Incumbent agreement: agreement / mean abs diff vs the current service is reported in the Job Summary (not gated)

Gateway Traffic Management

Traffic state lives in gateway-config.yml — the single source of truth. The deploy script writes the canary split; the engineer edits it to complete the cutover.

# gateway-config.yml (repo root, after deploy creates V12 service)
targets:
  - service: MLOPS_FRAUD_DETECTOR_SERVICE_V11
    weight: 80
  - service: MLOPS_FRAUD_DETECTOR_SERVICE_V12
    weight: 20

To complete cutover: edit gateway-config.yml to set V12 at 100%, remove V11, merge to main. The traffic-shift.yml workflow applies the gateway change and drops V11.

# After cutover (engineer edits and merges)
targets:
  - service: MLOPS_FRAUD_DETECTOR_SERVICE_V12
    weight: 100

Set serving.realtime.canary_weight: 100 in config.yml to skip the canary period and get instant cutover (same as a traditional blue/green deploy).

Model Monitoring

Snowflake ML Observability tracks prediction drift and feature distribution shifts in production. This framework sets up a MODEL MONITOR during PROD deployment that continuously evaluates model health.

Data Flow

1
Batch Inference
Scheduled Task appends predictions + MODEL_VERSION, SCORED_AT (TIMESTAMP_NTZ), RUN_ID to BATCH_PREDICTIONS.
→
2
Monitor Source View
BATCH_PREDICTIONS_MONITOR_SOURCE: predictions for the monitored version, LEFT JOINed to actuals when monitor.actuals.table is set. The monitor refreshes daily over a 7-day window.
→
3
Baseline
baseline: auto snapshots the promotion-time validation scoring into BATCH_PREDICTIONS_BASELINE.
→
4
Drift Alert
A Snowflake Alert logs to DRIFT_ALERTS when the drift metric (e.g., PSI) exceeds the threshold, and emails recipients when a notification integration is set.

Monitor Configuration

The monitor reads serving.batch.output_table through a source view and monitors model.predict_function. Settings live under monitor: in source/configs/config.yml:

monitor:
  monitor_name: FRAUD_DETECTOR_MONITOR
  timestamp_column: SCORED_AT
  prediction_column: output_feature_1   # score column monitored and used for drift
  refresh_interval: "1 day"
  aggregation_window: "7 days"
  actuals:                              # ground truth; enables performance metrics
    table: RAW_TRANSACTIONS             # in the source database/schema
    join_keys: [CUSTOMER_ID]
    label_sql: "MAX(IS_FRAUD::INT)"
  baseline: auto                        # auto | <table name> | null
  drift_metric: POPULATION_STABILITY_INDEX
  drift_threshold: 0.25
  alert_name: FRAUD_DETECTOR_DRIFT_ALERT
  alert_schedule: "1440 MINUTE"
  notification_integration: null        # EMAIL notification integration (optional)
  notification_recipients: []

Source View and Actuals

source/monitoring/model_monitor.py creates <output_table>_MONITOR_SOURCE, a view over the predictions filtered to the monitored version (MODEL_VERSION env var, or the model default). When monitor.actuals.table is set, the view LEFT JOINs label_sql (grouped by join_keys) as ACTUAL_LABEL, which the monitor uses as ACTUAL_CLASS_COLUMNS (binary) or ACTUAL_SCORE_COLUMNS (regression) so it reports performance metrics as well as drift. ID_COLUMNS are model.id_columns plus RUN_ID.

Baseline

The baseline setting controls whether drift detection is active:

ModeConfigurationWhat Happens
Auto (default)baseline: autoSnapshots the promotion-time validation scoring (<output_table>_VALIDATION) into <output_table>_BASELINE, so drift metrics work from day one and the drift alert is created.
Explicit tablebaseline: MY_BASELINE_TABLEUses the named table as the expected distribution.
Nonebaseline: nullMonitor collects prediction statistics over time. No drift metrics, no alert.

Drift Metrics

When a baseline is configured, the monitor can compute any of these drift metrics via MODEL_MONITOR_DRIFT_METRIC():

MetricWhat It MeasuresBest For
POPULATION_STABILITY_INDEX (PSI)Distribution shift between baseline and current predictions (binned comparison)Overall prediction drift. Industry standard for credit/fraud. <0.1 = stable, 0.1–0.25 = investigate, >0.25 = significant shift.
JENSEN_SHANNONSymmetric divergence between two distributions (0 = identical, 1 = completely different)Symmetric comparison. Works well for both continuous and categorical features.
WASSERSTEIN“Earth mover’s distance” — minimum cost to transform one distribution into anotherContinuous distributions. Sensitive to shifts in the tails.
DIFFERENCE_OF_MEANSSimple difference between average prediction valuesQuick sanity check. Large shift in mean prediction is an obvious red flag.

Set the metric with monitor.drift_metric. The default is POPULATION_STABILITY_INDEX.

Threshold Alerts

When a baseline is configured, the framework creates a Snowflake Alert that checks the drift metric daily:

-- Alert fires when PSI > 0.25 in the last 24 hours
CREATE ALERT FRAUD_DETECTOR_DRIFT_ALERT
    WAREHOUSE = SNOW_MLOPS_PROD_WH
    SCHEDULE = '1440 MINUTE'
    IF (EXISTS (
        SELECT 1 FROM TABLE(MODEL_MONITOR_DRIFT_METRIC(
            'FRAUD_DETECTOR_MONITOR', 'POPULATION_STABILITY_INDEX',
            'output_feature_1', '1 DAY'
        )) WHERE METRIC_VALUE > 0.25
           AND EVENT_TIMESTAMP > DATEADD('DAY', -1, CURRENT_TIMESTAMP())
    ))
    THEN
        INSERT INTO DRIFT_ALERTS (DRIFT_METRIC, THRESHOLD, STATUS)
        VALUES ('POPULATION_STABILITY_INDEX', 0.25, 'THRESHOLD_EXCEEDED');

Breaches are logged to a DRIFT_ALERTS table. When monitor.notification_integration and notification_recipients are set, the alert action also calls SYSTEM$SEND_EMAIL.

Custom Metrics

The native MODEL MONITOR handles built-in drift (PSI, Jensen–Shannon, Wasserstein), performance metrics (ROC_AUC, precision, recall), baseline comparison, segmentation, and the model monitoring dashboard. For a custom ML metric — such as a business score, dollar-weighted fraud loss, or a composite quality metric — use a different pattern:

  1. Calculate — Use a Snowflake Task (scheduled SQL) or ML Job to compute the metric on a schedule.
  2. Store — Write timestamped results to a table (e.g., CUSTOM_METRICS).
  3. Alert — Create a Snowflake Alert that checks the latest value against a threshold.

Example:

-- 1. Create the metrics table
CREATE TABLE IF NOT EXISTS CUSTOM_METRICS (
    METRIC_TS TIMESTAMP_NTZ DEFAULT CURRENT_TIMESTAMP(),
    METRIC_NAME VARCHAR,
    METRIC_VALUE FLOAT
);

-- 2. Schedule a task to compute the metric daily
CREATE OR REPLACE TASK COMPUTE_FRAUD_LOSS_TASK
    WAREHOUSE = SNOW_MLOPS_PROD_WH
    SCHEDULE = '1440 MINUTE'
AS
    INSERT INTO CUSTOM_METRICS (METRIC_NAME, METRIC_VALUE)
    SELECT 'FRAUD_LOSS_DOLLARS',
           SUM(CASE WHEN output_feature_1 > 0.5 AND IS_FRAUD = 1 THEN AMOUNT ELSE 0 END)
    FROM BATCH_PREDICTIONS bp
    JOIN RAW_TRANSACTIONS rt ON bp.TXN_ID = rt.TXN_ID
    WHERE bp.SCORED_AT > DATEADD('DAY', -1, CURRENT_TIMESTAMP());

-- 3. Alert when metric crosses a threshold
CREATE OR REPLACE ALERT FRAUD_LOSS_ALERT
    WAREHOUSE = SNOW_MLOPS_PROD_WH
    SCHEDULE = '1440 MINUTE'
    IF (EXISTS (
        SELECT 1 FROM CUSTOM_METRICS
        WHERE METRIC_NAME = 'FRAUD_LOSS_DOLLARS'
          AND METRIC_VALUE > 50000
          AND METRIC_TS > DATEADD('DAY', -1, CURRENT_TIMESTAMP())
    ))
    THEN
        INSERT INTO DRIFT_ALERTS (DRIFT_METRIC, THRESHOLD, STATUS)
        VALUES ('FRAUD_LOSS_DOLLARS', 50000, 'CUSTOM_THRESHOLD_EXCEEDED');

This pattern works for any metric that Snowflake’s native MODEL MONITOR doesn’t cover. Use the native monitor for what it does well (drift, performance, segmentation, dashboard), and custom Tasks + Alerts for business-specific metrics.

Experiment Tracking

Snowflake Experiments record training run parameters and metrics so you can compare models and select the best candidate for production.

API Pattern

from snowflake.ml.experiment import ExperimentTracking

exp = ExperimentTracking(session=session, database_name=db, schema_name=schema)
exp.set_experiment("FRAUD_DETECTION_TRAINING")

run_name = f"pipeline_{datetime.now().strftime('%Y%m%d_%H%M%S')}"
with exp.start_run(run_name):
    exp.log_params({"n_estimators": 100, "max_depth": 6, "learning_rate": 0.1})
    exp.log_params({"feature_view": "V1", "dataset_rows": "5000"})
    exp.log_metrics({"auc_roc": 0.94, "f1_score": 0.82, "precision": 0.85})

Key Constraints

  • log_metrics() only accepts numeric values (int/float). Filter non-numeric keys before calling.
  • log_params() accepts any string value — use it for metadata like feature view names, dataset sizes.
  • Runs inside @remote functions (ML Jobs) — experiment tracking works from compute pools.
  • Controlled by EXPERIMENT_CONFIG["enabled"] — can be toggled off without code changes.

Configuration

EXPERIMENT_CONFIG = {
    "enabled": "true",
    "experiment_name": "FRAUD_DETECTION_TRAINING",
    "run_name_prefix": "pipeline",
}

Testing

Unit tests run on every PR and push with no Snowflake connection; integration tests need a live PROD deployment.

Unit Tests: tests/test_config.py, test_pipeline_steps.py, test_gap_fillers.py

Run on every PR and push — no Snowflake connection needed. Tests:

  • Config values are the right types; required keys exist; every STEPS entry resolves to a step package exposing run(session)
  • ML_RUNTIME_DEPS matches pyproject.toml [dependency-groups] ml-runtime and every dep is pinned with ==
  • Gate rules reference metrics produced for the configured task_type; min/max rules, boundary values, and missing metrics
  • Champion/challenger: disabled, no champion, higher/lower-is-better, and improvement margins
  • Metrics per task type, signature-based output validation, data-check SQL and rules
  • Serving flags, gateway target parsing/weight validation/file round-trip, canary split, monitor source SQL, and batch Task wiring
# Run unit tests (no Snowflake required)
uv run pytest tests/ -v --ignore=tests/test_endpoint.py

Integration Tests: tests/test_endpoint.py

Require a live PROD deployment — run manually after a successful deploy-prod job. Tests:

  • Gateway exists and has a provisioned ingress URL
  • Active SPCS service behind the gateway is READY
  • Service endpoint is publicly accessible
  • predict_proba returns two columns (output_feature_0, output_feature_1)
  • Probabilities sum to 1.0 (within 0.01 tolerance)
  • Batch of 3 rows returns 3 results
  • A suspicious profile gets a higher fraud probability than a clean one
# Run integration tests (requires live PROD service)
SNOWFLAKE_CONNECTION_NAME=your-connection uv run pytest tests/test_endpoint.py -v
Integration tests are excluded from CI by default The CI workflow runs pytest tests/ -v --ignore=tests/test_endpoint.py. Run test_endpoint.py manually after deployment to validate the live service, or add a post-deploy CI step if you want automated smoke testing.

Environment Overrides

Per-environment infrastructure names live under environments: in the same file and are selected by --env on the DAG (dev, stage, or prod):

environments:
  dev:
    database: SNOW_MLOPS_DEV
    warehouse: SNOW_MLOPS_DEV_WH
    compute_pool: SNOW_MLOPS_DEV_POOL
  stage:
    database: SNOW_MLOPS_STAGE
    warehouse: SNOW_MLOPS_STAGE_WH
    compute_pool: SNOW_MLOPS_STAGE_POOL
  prod:
    database: SNOW_MLOPS_PROD
    warehouse: SNOW_MLOPS_PROD_WH
    compute_pool: SNOW_MLOPS_PROD_POOL
returning a flat dict of primitives:

from config import resolve_env_config

cfg = resolve_env_config("stage")
# {"env": "stage", "database": "SNOW_MLOPS_STAGE", "warehouse": ..., "compute_pool": ...}

The DAG uses it to pick the target infrastructure and pins those names into each task's environment. source/monitoring/model_monitor.py uses the same function to resolve its environment.

Adding a New Pipeline Step

  1. Create source/<name>/ with a logic module exposing run(session) -> dict and an entrypoint.py
  2. Add an entry to STEPS in source/pipeline/train_dag.py (module, config key, pip deps), append it to STEP_ORDER, and add the package to STAGED_PACKAGES
  3. Add a pipeline_steps.<name> block to source/configs/config.yml

No new dispatch code is required — both the ML Job and the stored procedure wrapper are built generically, and steps are chained in STEP_ORDER.
