MLOps on Snowflake

End-to-end architecture and workflow guide for production ML pipelines using Snowflake-native services.

This document describes a complete MLOps framework built entirely on Snowflake. It covers every step from feature engineering through production deployment, including two inference modes (batch and real-time), automated CI/CD, quality gates, and zero-downtime model upgrades. The framework is demonstrated with a fraud detection model but applies to any ML problem.

Note — Single-Account Example

This guide demonstrates the MLOps workflow using a single Snowflake account with environments separated at the database level (DEV, STAGE, PROD). This is the simplest topology and ideal for getting started. The architecture is designed to extend to multi-account deployments (separate accounts per environment, cross-account model sharing) and cross-region replication — see the Pluggable promotion topology section for details on how to configure these patterns.

🏗Overview & Architecture

The pipeline moves ML models from experimentation to production through three environments. All environments exist within a single Snowflake account, separated at the database level. Source data always lives in PROD; DEV and STAGE read from PROD for training but write artifacts to their own databases.

📊Feature Store

Features are defined as Snowflake Feature Views backed by Dynamic Tables. You declare the transformation SQL once; Snowflake handles scheduling, refresh, and serving. The Feature Store API provides entity registration, versioning, and point-in-time correctness.

How it works

A Feature View is a Dynamic Table that computes features from source data. The framework registers Feature Views as the first step in every pipeline run. Registration is idempotent — safe to call repeatedly without side effects.

Step 1: Define entities

Entities define the join keys for feature lookups. They must be registered before any Feature View that references them.

from snowflake.ml.feature_store import Entity

customer_entity = Entity(name="CUSTOMER", join_keys=["CUSTOMER_ID"])
transaction_entity = Entity(name="TRANSACTION", join_keys=["CUSTOMER_ID", "TRANSACTION_ID"])

Step 2: Define feature SQL

feature_df = session.sql("""
    SELECT
        t.CUSTOMER_ID,
        COUNT(*)                          AS TOTAL_TXN_COUNT,
        AVG(t.AMOUNT)                     AS AVG_TXN_AMOUNT,
        MAX(t.AMOUNT)                     AS MAX_TXN_AMOUNT,
        STDDEV(t.AMOUNT)                  AS STDDEV_TXN_AMOUNT,
        COUNT(DISTINCT t.MERCHANT_ID)     AS UNIQUE_MERCHANTS,
        SUM(CASE WHEN t.IS_FRAUD=1 THEN 1 ELSE 0 END) AS HISTORICAL_FRAUD_COUNT,
        AVG(t.IS_FRAUD)                   AS HISTORICAL_FRAUD_RATE,
        COUNT(DISTINCT DATE(t.TX_TIMESTAMP)) AS ACTIVE_DAYS,
        c.CREDIT_SCORE,
        c.ACCOUNT_AGE_DAYS,
        c.ANNUAL_INCOME
    FROM RAW_TRANSACTIONS t
    JOIN CUSTOMER_PROFILES c ON t.CUSTOMER_ID = c.CUSTOMER_ID
    GROUP BY ALL
""")

Step 3: Register the Feature View

from snowflake.ml.feature_store import FeatureStore, FeatureView

fs = FeatureStore(session=session, database=database, schema=schema)

# Entity MUST be registered first
fs.register_entity(customer_entity)

fv = FeatureView(
    name="CUSTOMER_RISK_FEATURES",
    entities=[customer_entity],
    feature_df=feature_df,
)

fs.register_feature_view(
    feature_view=fv,
    version="V1",
    refresh_freq="60 minutes",
    overwrite=True,    # Idempotent — recreates if exists
)

This creates a Dynamic Table named CUSTOMER_RISK_FEATURES$V1 in the target schema. The $V1 suffix is the Feature Store's version convention.

Important

You must call fs.register_entity() before fs.register_feature_view(). If the entity doesn't exist, registration fails with: "Entity CUSTOMER has not been registered."

Feature versioning

Feature View versions are tracked manually in source/config.py:

FEATURE_VIEW_NAME = "CUSTOMER_RISK_FEATURES"
FEATURE_VIEW_VERSION = "V1"  # Bump to "V2" when feature SQL changes

When you bump the version, the next pipeline run creates a new Dynamic Table (CUSTOMER_RISK_FEATURES$V2) alongside the old one. The model comment records which feature version it was trained on, providing full lineage.

When to bump: Only when the feature SQL changes (new columns, different aggregations, changed filters). If the same SQL produces different results because source data changed, that's a model retrain — not a feature version bump.

Feature promotion across environments

Feature Views cannot be replicated like models. A Dynamic Table is a live computation, not a static artifact. Promotion means re-running the same registration code against the target database:

# In the STAGE pipeline:
register_feature_views(session, database="SNOW_MLOPS_STAGE", schema="ML")

# The same function runs in DEV (no args = use config defaults):
register_feature_views(session)

Refresh strategies by environment

EnvironmentFeature ViewRefresh FrequencyRationale
DEVYesOn-demandAvoid unnecessary compute during development
STAGEYesOnce per pipeline runOnly needs features for CI training validation
PROD (offline)NoN/AClient sends features in inference request
PROD (online)Yes10 minutesService looks up features at inference time

Offline vs online serving

Offline serving (current implementation)

The client computes or retrieves features before calling the inference endpoint. No Feature View needed in PROD. Simpler CI/CD — only the model is replicated.

Online serving (future)

The inference service fetches features from a Snowflake Postgres instance at request time. The Dynamic Table syncs to Postgres with ~10s target lag. The client sends only an entity key (e.g., CUSTOMER_ID).

🏋Model Training

Training runs on Snowflake Compute Pools using the @remote decorator from snowflake.ml.jobs. The decorator serializes your Python function and executes it inside a managed container with full Snowflake SQL access.

How @remote works

  1. Serialization: cloudpickle serializes the function body and its closure (captured local variables)
  2. Upload: The serialized payload is uploaded to an internal stage
  3. Scheduling: Snowflake schedules the function on an available node in the compute pool
  4. Execution: The container starts, installs pip_requirements, runs the function
  5. Return: The return value is sent back to the caller (your laptop or CI runner)

Training function pattern

from snowflake.ml.jobs import remote

@remote(
    "SNOW_MLOPS_STAGE_POOL",                  # Compute pool to run on
    stage_name="@SNOW_MLOPS_STAGE.ML.JOB_STAGE",  # Where to store the serialized function
    pip_requirements=[                         # Packages installed in the container
        "xgboost",
        "scikit-learn",
        "snowflake-ml-python",
    ],
)
def train_and_register_stage() -> str:
    """Runs inside the Snowflake container. Returns JSON with metrics."""
    from snowflake.snowpark import Session
    from snowflake.ml.registry import Registry
    import xgboost as xgb

    # Get an authenticated session inside the container
    session = Session.builder.getOrCreate()

    # Load training data from Feature Store Dynamic Table
    df = session.sql("SELECT ... FROM CUSTOMER_RISK_FEATURES$V1 ...").to_pandas()

    # Train
    model = xgb.XGBClassifier(n_estimators=200, learning_rate=0.1, max_depth=6)
    model.fit(X_train, y_train)

    # Register to Model Registry
    reg = Registry(session=session, database_name="SNOW_MLOPS_STAGE", schema_name="ML")
    reg.log_model(
        model=model,
        model_name="MLOPS_FRAUD_DETECTOR",
        version_name="V2",  # Auto-computed from existing versions
        target_platforms=["WAREHOUSE", "SNOWPARK_CONTAINER_SERVICES"],
        conda_dependencies=["xgboost", "scikit-learn"],
        sample_input_data=X_test.head(10),
    )

    return json.dumps({"status": "success", "metrics": {...}, "version": "V2"})

Critical patterns

Closure capture

External references (table names, config values) must be captured as local variables before the function definition. cloudpickle serializes the function's closure, not module state:

# Captured as closure variables — works inside @remote
_FV_TABLE = f'"CUSTOMER_RISK_FEATURES$V1"'
_DATABASE = "SNOW_MLOPS_STAGE"

@remote(...)
def train():
    # Can reference _FV_TABLE and _DATABASE inside here
    df = session.sql(f"SELECT * FROM {_DATABASE}.ML.{_FV_TABLE}").to_pandas()

Session inside the container

The function takes no arguments. Inside the container, call Session.builder.getOrCreate() to get an authenticated session. Do not pass a session object as a parameter.

pip_requirements (not packages)

Use pip_requirements=[], not packages=[]. The packages parameter is silently ignored by @remote.

What happens during execution

PhaseDurationWhat happens
Cold start1-3 minCompute pool node starts (if suspended)
Container setup1-2 minPull base image, install pip_requirements
Training1-5 minExecute the function body
Model logging1-2 minPackage model for both WAREHOUSE and SPCS targets

Total wall-clock time: ~5-12 minutes per training run (cold start adds time on first run after pool suspension).

📦Model Registry

The Snowflake Model Registry stores trained models as versioned database objects. Each model has versions (V1, V2, ...), a default version, aliases, and SQL-level access control. Models are first-class Snowflake objects — they support RBAC, replication, and can be called directly from SQL.

Auto-versioning

Model versions are not stored in config files. They are computed at runtime by querying the registry:

# Inside the training function:
try:
    versions_df = session.sql(f"SHOW VERSIONS IN MODEL {db}.{schema}.{model_name}").collect()
    existing = [r["name"] for r in versions_df]
    max_v = max(int(v.replace("V", "")) for v in existing if v.startswith("V") and v[1:].isdigit())
    version_name = f"V{max_v + 1}"
except Exception:
    version_name = "V1"  # First version if model doesn't exist yet

Every pipeline run — whether triggered by a code push or manual dispatch — produces the next sequential version. No file edits needed.

Registration with target_platforms

reg.log_model(
    model=model,
    model_name="MLOPS_FRAUD_DETECTOR",
    version_name=version_name,
    conda_dependencies=["xgboost", "scikit-learn"],
    sample_input_data=X_test.head(10),
    target_platforms=["WAREHOUSE", "SNOWPARK_CONTAINER_SERVICES"],
    comment=f"features:{_FV_TABLE} | AUC={metrics['auc_roc']:.4f} | git:{git_sha}",
)
Important

The target_platforms parameter is critical. Without it, models default to SPCS-only and cannot be used for warehouse-based batch inference. Always include ["WAREHOUSE", "SNOWPARK_CONTAINER_SERVICES"] to support both inference modes.

What target_platforms controls

Traceability

The model comment records a complete audit trail:

  • Feature version: Which feature view was used for training
  • Metrics: AUC-ROC, F1, precision at registration time
  • Git SHA: Exact commit that produced this model version

This enables answering "what changed?" between any two model versions without searching CI logs.

Cross-database replication

Models are promoted from STAGE to PROD using atomic SQL replication:

-- Copy version V3 from STAGE to PROD
ALTER MODEL SNOW_MLOPS_PROD.ML.MLOPS_FRAUD_DETECTOR
  ADD VERSION V3
  FROM MODEL SNOW_MLOPS_STAGE.ML.MLOPS_FRAUD_DETECTOR VERSION V3;

-- Make it the active version
ALTER MODEL SNOW_MLOPS_PROD.ML.MLOPS_FRAUD_DETECTOR
  SET DEFAULT_VERSION = V3;

This preserves all metadata, signatures, and target_platforms configuration. The PROD model is immediately usable for both batch and real-time inference.

✅Quality Gate

The quality gate blocks models that don't meet minimum performance thresholds from being promoted to PROD. It runs after training and before replication.

How it works

# source/config.py — thresholds
MIN_AUC_ROC = 0.85
MIN_PRECISION = 0.70
MIN_RECALL = 0.60

# scripts/run_stage_pipeline.py — gate logic
def check_quality_gate(metrics: dict) -> tuple[bool, list[str]]:
    failures = []
    if metrics.get("auc_roc", 0) < MIN_AUC_ROC:
        failures.append(f"AUC-ROC {metrics['auc_roc']:.4f} < {MIN_AUC_ROC}")
    if metrics.get("precision", 0) < MIN_PRECISION:
        failures.append(f"Precision {metrics['precision']:.4f} < {MIN_PRECISION}")
    if metrics.get("recall", 0) < MIN_RECALL:
        failures.append(f"Recall {metrics['recall']:.4f} < {MIN_RECALL}")
    return len(failures) == 0, failures

What happens on failure

  1. The model IS registered in STAGE (for debugging/analysis)
  2. The model is NOT replicated to PROD
  3. The CI workflow exits with code 1 (failed status)
  4. Metrics are still posted to the GitHub Job Summary and PR comment

CI reporting

⚡Inference (Batch & Real-Time)

The framework supports two inference modes. Both can run simultaneously — they serve different use cases.

Batch inference (warehouse-based)

Scores an entire table using the registered model running on warehouse compute. No SPCS service or compute pool needed. Used for populating prediction tables consumed by dashboards, alerts, or downstream pipelines.

How it works

from snowflake.ml.registry import Registry

def run_batch_inference(session, input_table, output_table, model_name):
    reg = Registry(session=session)
    model = reg.get_model(model_name)
    mv = model.default                       # Uses DEFAULT_VERSION

    input_df = session.table(input_table)    # e.g., CUSTOMER_RISK_FEATURES$V1
    predictions_df = mv.run(input_df, function_name="predict_proba")

    predictions_df.write.mode("overwrite").save_as_table(output_table)
    return predictions_df.count()

Output schema

The model.run() method appends prediction columns to the input DataFrame. For a binary classifier with predict_proba:

ColumnDescription
(all input columns)Passed through unchanged
output_feature_0Probability of class 0 (not fraud)
output_feature_1Probability of class 1 (fraud)
Note

Output columns use lowercase names (output_feature_0). In Snowpark, reference them with quoted identifiers: '"output_feature_0"'.

Validation

After scoring, the pipeline validates predictions:

  • No null predictions (model didn't error on any row)
  • Probabilities sum to ~1.0 (within 0.01 tolerance)
  • If validation fails, the CI workflow exits with code 1

When batch runs

STAGEAfter model registration (CI step)CUSTOMER_RISK_FEATURES$V1BATCH_PREDICTIONS
PRODAfter SPCS deploy (CI step)CUSTOMER_RISK_FEATURES$V1BATCH_PREDICTIONS

Real-time inference (SPCS + Gateway)

Registered models are deployed as containerized REST services on Snowpark Container Services (SPCS). Snowflake Gateway provides a stable URL that persists across model upgrades.

Deploying a service

from snowflake.ml.registry import Registry

reg = Registry(session=session, database_name="SNOW_MLOPS_PROD", schema_name="ML")
model = reg.get_model("MLOPS_FRAUD_DETECTOR")
mv = model.version("V3")

mv.create_service(
    service_name="MLOPS_FRAUD_DETECTOR_SERVICE_V3",
    service_compute_pool="SNOW_MLOPS_PROD_POOL",
    image_build_compute_pool="SNOW_MLOPS_PROD_POOL",
    ingress_enabled=True,
    max_instances=2,
)

Snowflake Gateway and blue/green deployment

The Gateway provides a permanent hostname that routes traffic to underlying services. During model upgrades, the URL does not change — only the routing target shifts.

flowchart LR
    CLIENT[API Clients] --> GW["Gateway (stable URL)"]
    GW -->|"100%"| V3["SERVICE_V3 (new)"]
    OLD["SERVICE_V2 (old)"] -.->|"dropped after shift"| X[fa:fa-trash]

Blue/green deployment flow

  1. Deploy new service: Create MLOPS_FRAUD_DETECTOR_SERVICE_V3 alongside the existing service
  2. Wait for READY: Poll SYSTEM$GET_SERVICE_STATUS() until all instances are ready
  3. Health check: Run a sample prediction against the new service directly
  4. Create gateway (if first deploy): CREATE GATEWAY ... FROM SPECIFICATION
  5. Shift traffic: ALTER GATEWAY ... SET ROUTES — 100% to new service (atomic)
  6. Cleanup: Drop the old service
-- Atomic traffic shift to new service
ALTER GATEWAY SNOW_MLOPS_PROD.ML.FRAUD_DETECTOR_GATEWAY
FROM SPECIFICATION $$
  spec:
    type: traffic_split
    split_type: custom
    targets:
      - type: endpoint
        value: SNOW_MLOPS_PROD.ML.MLOPS_FRAUD_DETECTOR_SERVICE_V3!inference
        weight: 100
$$;

Zero downtime: the gateway atomically switches from old to new. Clients see no interruption.

🚀Environment Promotion

Code and models flow through three environments with automated validation and manual approval gates.

Two promotion triggers

The STAGE pipeline can be triggered in two ways:

TriggerWhen to useHowExample
Code PromotionFeature engineering, hyperparameters, or pipeline code changedPush/merge to main (automatic)Add a new feature column, change n_estimators
Model PromotionRetrain on fresh data, no code changesManual dispatch via GitHub Actions "Run workflow"New month of data arrived, want a fresh model

Both triggers execute the identical pipeline: register features → train → quality gate → replicate → batch inference. The only difference is what initiated the run.

Model versioning (auto-increment)

Model versions are derived at runtime from the Model Registry — not from any config file. The training function queries "what versions exist?" and computes the next sequential number:

V1 (first run) → V2 (next run) → V3 (next run) → ...

Whether triggered by a code change or manual dispatch, every run produces V(n+1). The model comment records the git SHA, feature version, and metrics for traceability.

Note

Feature View versions (FEATURE_VIEW_VERSION = "V1" in config.py) are the one version you bump manually — and only when the feature SQL itself changes. Everything else is automatic.

OIDC authentication

GitHub Actions authenticates to Snowflake using OIDC. GitHub mints a short-lived JWT; Snowflake validates the issuer and subject claim. No passwords or API keys are stored anywhere.

sequenceDiagram

    GH->>GH: Mint OIDC JWT (short-lived)
    GH->>SF: Present JWT with subject claim
    SF->>SF: Validate issuer + subject
    SF-->>GH: Session token (SNOWFLAKE_TOKEN)
    GH->>SF: Execute pipeline via Python SDK

Session helper (snowpark_session.py)

The session helper detects whether it's running in CI or locally and creates the appropriate session:

def create_snowpark_session():
    # CI/OIDC: detected by SNOWFLAKE_TOKEN + SNOWFLAKE_ACCOUNT in env
    if os.getenv("SNOWFLAKE_TOKEN") and os.getenv("SNOWFLAKE_ACCOUNT"):
        config = {
            "account": os.environ["SNOWFLAKE_ACCOUNT"],
            "token": os.environ["SNOWFLAKE_TOKEN"],
            "authenticator": os.getenv("SNOWFLAKE_AUTHENTICATOR", "oauth"),
        }
        # Pass OIDC-specific params
        if os.getenv("SNOWFLAKE_WORKLOAD_IDENTITY_PROVIDER"):
            config["workload_identity_provider"] = os.environ["SNOWFLAKE_WORKLOAD_IDENTITY_PROVIDER"]
        if os.getenv("SNOWFLAKE_AUDIENCE"):
            config["audience"] = os.environ["SNOWFLAKE_AUDIENCE"]
        # Add database/schema/role/warehouse from env
        ...
        return Session.builder.configs(config).create()

    # Local dev: use connections.toml
    connection_name = os.getenv("SNOWFLAKE_CONNECTION_NAME", "default")
    return Session.builder.configs({"connection_name": connection_name}).create()
Important

The authenticator is WORKLOAD_IDENTITY, not oauth. If you hardcode "oauth", CI fails with "Invalid OAuth access token." Always read it from the environment variable.

The project uses uv dependency groups to separate CI from dev dependencies:

# pyproject.toml
[dependency-groups]
snow = [
    "snowflake-snowpark-python>=1.53.1",
    "snowflake-ml-python>=1.47.0",
]
dev = ["ruff", "pytest"]

CI runs: uv sync --group snow --no-default-groups — installs only the Snowflake packages needed for orchestration. Dev tools (ruff, pytest) are not installed in the deploy workflow.

🔒RBAC & Security

CI/CD uses a least-privilege role (MLOPS_DEPLOY_ROLE) — never ACCOUNTADMIN. This role has exactly the permissions needed to run the pipeline and nothing more.

MLOPS_DEPLOY_ROLE permissions

CategoryGrants
Database accessUSAGE on all three databases (DEV, STAGE, PROD)
Schema controlALL on .ML schema in each database
ObjectsALL on all tables, dynamic tables, stages, models in each schema
ComputeUSAGE on all warehouses and compute pools
Account-levelBIND SERVICE ENDPOINT, EXECUTE TASK, EXECUTE MANAGED TASK

Model ownership

Models are Snowflake objects with ownership-based access control. A role can only modify models it owns. The setup script transfers ownership of any existing models to MLOPS_DEPLOY_ROLE:

-- Transfer existing models (created by ACCOUNTADMIN during initial setup)
GRANT OWNERSHIP ON ALL MODELS IN SCHEMA SNOW_MLOPS_DEV.ML TO ROLE MLOPS_DEPLOY_ROLE COPY CURRENT GRANTS;
GRANT OWNERSHIP ON ALL MODELS IN SCHEMA SNOW_MLOPS_STAGE.ML TO ROLE MLOPS_DEPLOY_ROLE COPY CURRENT GRANTS;
GRANT OWNERSHIP ON ALL MODELS IN SCHEMA SNOW_MLOPS_PROD.ML TO ROLE MLOPS_DEPLOY_ROLE COPY CURRENT GRANTS;
Important

Without this ownership transfer, CI fails with: "Model 'MLOPS_FRAUD_DETECTOR' already exists, but current role has no privileges on it." This happens because setup.sh creates infra as ACCOUNTADMIN, but CI runs as MLOPS_DEPLOY_ROLE.

Service users

Each GitHub environment has its own service user with OIDC workload identity:

CREATE USER SVC_GITHUB_ACTIONS_STAGE
  TYPE = SERVICE
  DEFAULT_ROLE = MLOPS_DEPLOY_ROLE
  WORKLOAD_IDENTITY = (
    TYPE = OIDC
    ISSUER = 'https://token.actions.githubusercontent.com'
    SUBJECT = 'repo:owner@ID/repo@ID:environment:STAGE'
  );

ALTER USER SVC_GITHUB_ACTIONS_STAGE SET NETWORK_POLICY = 'GITHUB_ACTIONS_POLICY';

Network policy

GitHub Actions runners use dynamic IPs. Snowflake provides a managed network rule that automatically tracks them:

CREATE NETWORK POLICY GITHUB_ACTIONS_POLICY
  ALLOWED_NETWORK_RULE_LIST = ('SNOWFLAKE.NETWORK_SECURITY.GITHUBACTIONS_GLOBAL');

This is applied to service users only — it doesn't affect human users or other integrations.
