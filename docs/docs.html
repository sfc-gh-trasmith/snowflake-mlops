MLOps on Snowflake

Architecture and Workflow Guide — Task DAG Orchestration with ML Jobs

Overview

This framework implements a complete MLOps lifecycle on Snowflake using native services. The pipeline is orchestrated as a Snowflake Task DAG (Python SDK) where each step runs as an ML Job on a compute pool (SPCS) or as a stored procedure on a warehouse.

Task DAG Orchestration

The pipeline is defined using the Python SDK (snowflake.core.task.dagv1) which provides a programmatic interface for creating and managing Snowflake Tasks. This approach is preferred over raw SQL because it's easier to modify, test, and integrate with CI/CD.

Key Components

SDK ClassPurpose
DAGContainer for the task graph; defines root task name and warehouse
DAGTaskIndividual task (step) within the DAG
DAGOperationOperations on the DAG: deploy, run, get status
StoredProcedureCallWarehouse-mode task definition (SQL/Python sproc)
@remoteML Job definition (runs on compute pool via SPCS)

Configurable Compute Per Step

Each pipeline step can run on either a warehouse WH or a compute pool SPCS, configured via source/config.py:

PIPELINE_CONFIG = {
    "feature_engineering_compute": "spcs",   # "warehouse" or "spcs"
    "training_compute": "spcs",
    "evaluation_compute": "spcs",
    ...
}
ModeWhen to UseImplementation
SPCSGPU training, custom packages, heavy computeDAGTask(definition=@remote_func)
WHSQL-heavy, lightweight Python, cost-sensitiveDAGTask(definition=StoredProcedureCall(...))

DAG Definition Pattern

from snowflake.core.task.dagv1 import DAG, DAGOperation, DAGTask
from snowflake.ml.jobs import remote

# Build @remote-decorated functions (ML Jobs)
fe_func = build_feature_eng_remote(cfg)
train_func = build_train_model_remote(cfg)
eval_func = build_evaluate_remote(cfg)

# Define DAG with dependency chain
with DAG("ML_TRAINING_PIPELINE", warehouse=wh) as dag:
    fe_task = DAGTask("FEATURE_ENG", definition=fe_func)
    train_task = DAGTask("TRAIN_MODEL", definition=train_func)
    eval_task = DAGTask("EVALUATE", definition=eval_func)
    fe_task >> train_task >> eval_task

# Deploy to Snowflake
schema_ref = root.databases[db].schemas[schema]
dag_op = DAGOperation(schema_ref)
dag_op.deploy(dag, mode=CreateMode.or_replace)

Task Naming Convention

The Python SDK prefixes child task names with the DAG name:

  • Root: ML_TRAINING_PIPELINE
  • Children: ML_TRAINING_PIPELINE$FEATURE_ENG, ML_TRAINING_PIPELINE$TRAIN_MODEL, ML_TRAINING_PIPELINE$EVALUATE

CLI Usage

# Deploy the DAG (creates/replaces tasks)
python source/pipeline/ml_pipeline_dag.py --deploy --env stage

# Execute (triggers the root task)
python source/pipeline/ml_pipeline_dag.py --execute --env stage

# Show recent task history
python source/pipeline/ml_pipeline_dag.py --status --env stage

Model Training (ML Jobs)

Training runs as an ML Job on a compute pool using the @remote decorator from snowflake.ml.jobs. The function is serialized via cloudpickle and executed in an isolated container.

Training Function Pattern

@remote(
    pool_name,
    stage_name="@DB.SCHEMA.PIPELINE_STAGE",
    pip_requirements=["xgboost", "scikit-learn", "snowflake-ml-python"],
)
def train_model() -> str:
    import json                          # MUST be inside for cloudpickle
    import numpy as np
    import xgboost as xgb
    from snowflake.snowpark import Session as _Session

    session = _Session.builder.getOrCreate()
    # ... load data, train, evaluate, save artifacts
    return json.dumps(result)
Important: cloudpickle Serialization Rules

All imports MUST be inside the @remote function body. Module references from outer scope may not serialize correctly. Closure variables (strings, dicts) are captured fine.

Training Details

  • Algorithm: XGBoost (XGBClassifier)
  • Validation: 5-fold stratified cross-validation
  • Class imbalance: scale_pos_weight=33 (~3% fraud rate)
  • Artifacts saved to stage: model.ubj, sample_input.json
  • Metrics written to: PIPELINE_RESULTS table

SQL for Results Table

-- PARSE_JSON() not allowed in VALUES clause; use INSERT...SELECT
INSERT INTO DB.SCHEMA.PIPELINE_RESULTS (STEP, STATUS, RESULT, CREATED_AT)
SELECT 'training', 'SUCCESS', PARSE_JSON('{"metrics": {...}}'), CURRENT_TIMESTAMP()

Model Registry

After training passes the quality gate, the model is registered in Snowflake's Model Registry with auto-incremented versioning.

Registration Flow

  1. Download model.ubj from PIPELINE_STAGE/artifacts/
  2. Load model into XGBClassifier
  3. Query existing versions: SHOW VERSIONS IN MODEL ...
  4. Auto-increment: V11 → V12
  5. Register with conda_dependencies=["xgboost==3.3.0", "scikit-learn"]
  6. Set as DEFAULT version
Conda Version Pinning

The conda_dependencies must reference versions available in Snowflake's Anaconda channel. Pin to a specific version (e.g., xgboost==3.3.0) rather than relying on automatic resolution which may pick an unavailable version.

Quality Gate Thresholds

MetricThresholdPurpose
AUC-ROC≥ 0.60Discriminative power
Precision≥ 0.03False positive control
Recall≥ 0.30Fraud detection coverage

If any threshold fails, the workflow exits with code 1 and the model is not registered.

Inference (Batch & Real-Time)

Batch Inference

Batch inference scores the entire Feature View table using the default model version from the Model Registry. It runs on a warehouse (no SPCS service needed) and writes predictions to an output table.

Architecture

Feature View Table              Model Registry               Output Table
┌─────────────────────────┐   ┌───────────────────────┐   ┌────────────────────────┐
│ CUSTOMER_RISK_FEATURES  │   │ MLOPS_FRAUD_DETECTOR  │   │ BATCH_PREDICTIONS      │
│ $V1 (5000 rows)         │──>│ .default (V12)        │──>│ (5000 scored rows)     │
│                         │   │                       │   │                        │
│ 12 feature columns      │   │ mv.run(input_df,      │   │ + output_feature_0     │
│                         │   │   "predict_proba")    │   │ + output_feature_1     │
└─────────────────────────┘   └───────────────────────┘   └────────────────────────┘
         │                             │                              │
         └──── Warehouse compute ──────┘                              ▼
                                                            Validation checks:
                                                            - No NULL predictions
                                                            - P(0)+P(1) ≈ 1.0

When It Runs

CI/CD StageEnvironmentPurpose
deploy-stage (step 5)STAGEValidate newly registered model works
deploy-prod (step 2)PRODValidate model runs correctly in PROD

Code Pattern

from snowflake.ml.registry import Registry

reg = Registry(session, database_name="SNOW_MLOPS_PROD", schema_name="ML")
model = reg.get_model("MLOPS_FRAUD_DETECTOR")
mv = model.default                              # Current DEFAULT version (e.g., V12)

input_df = session.table('DB.SCHEMA."CUSTOMER_RISK_FEATURES$V1"')
predictions_df = mv.run(input_df, function_name="predict_proba")

predictions_df.write.mode("overwrite").save_as_table("BATCH_PREDICTIONS")

Output Schema

ColumnTypeDescription
(all input features)-Passed through from input
output_feature_0FLOATP(legitimate) — probability of class 0
output_feature_1FLOATP(fraud) — probability of class 1

Validation Checks

  • No NULLs: If any prediction is NULL, the model failed to score that row (exit code 1)
  • Probability sanity: P(class0) + P(class1) must be within 0.01 of 1.0

How It Works Under the Hood

When the model was registered with conda_dependencies=["xgboost==3.3.0", "scikit-learn"], Snowflake created a vectorized Python UDF backed by the serialized model. mv.run() invokes that UDF over the input DataFrame — all computation stays inside the warehouse, no data leaves Snowflake, no SPCS service needed.

FileRole
scripts/run_batch_inference.pyCI entry point: orchestrates scoring + validation
source/serving/batch_inference.pyCore logic: run_batch_inference() and validate_predictions()

Real-Time Inference (SPCS + Gateway)

The latest model version is deployed as a containerized SPCS service behind a Snowflake Gateway for HTTP access. Uses a blue/green deployment strategy for zero-downtime rollouts.

┌───────────────────┐       ┌─────────────────────────────┐     ┌──────────────────────┐

                            │   - REST endpoint /inference│     │                      │
                            │   - max_instances: 2        │     │ ingress_url: https://│

                                                                  (HTTPS requests)

Blue/Green Deployment Flow (6 steps)

StepActionDetail
1Get latest model versionSHOW MODELS → reads default_version_name (e.g., V12)
2Determine service namesNew: MLOPS_FRAUD_DETECTOR_SERVICE_V12, Old: ..._V11
3Create new versioned servicemv.create_service() — builds container image on compute pool
4Wait for READYPolls SYSTEM$GET_SERVICE_STATUS() every 15s, up to 10 min
5Health checkTest prediction via mv.run(sample, service_name=...)
6Shift traffic + cleanupALTER GATEWAY → 100% to new service, then DROP SERVICE old

Service Creation

from snowflake.ml.registry import Registry

reg = Registry(session, database_name="SNOW_MLOPS_PROD", schema_name="ML")
mv = reg.get_model("MLOPS_FRAUD_DETECTOR").version("V12")

mv.create_service(
    service_name="MLOPS_FRAUD_DETECTOR_SERVICE_V12",
    service_compute_pool="SNOW_MLOPS_PROD_POOL",
    image_build_compute_pool="SNOW_MLOPS_PROD_POOL",
    ingress_enabled=True,
    max_instances=2,
)

Health Check

Before shifting traffic, a test prediction is sent directly to the new service:

# Targets the new service specifically (bypasses gateway)
result = mv.run(sample_df, function_name="predict_proba",
                service_name="MLOPS_FRAUD_DETECTOR_SERVICE_V12")

# Validates:
# - output_feature_0 and output_feature_1 columns exist
# - Probabilities sum to ~1.0 (within 0.01 tolerance)

Gateway Traffic Shift

ALTER GATEWAY SNOW_MLOPS_PROD.ML.FRAUD_DETECTOR_GATEWAY
FROM SPECIFICATION $$
  spec:
    type: traffic_split
    split_type: custom
    targets:
      - type: endpoint
        value: SNOW_MLOPS_PROD.ML.MLOPS_FRAUD_DETECTOR_SERVICE_V12!inference
        weight: 100
$$

Rollback

If the real-time service has issues after deployment, the rollback.yml workflow:

  1. Sets model DEFAULT back to previous version (e.g., V11)
  2. Runs deploy_prod_service.py again → creates _V11 service, shifts gateway back
  3. Drops the broken _V12 service

CI uses OIDC workload identity (zero secrets stored in GitHub). The Snowflake CLI action handles token exchange automatically.

EnvironmentService User
STAGESVC_GITHUB_ACTIONS_STAGE
PRODSVC_GITHUB_ACTIONS

Workflow: pr-checks.yml

Triggered on PRs to main. Runs lint and unit tests. Both must pass before merge is allowed (branch protection).

Release Tagging

On successful PROD deployment, the workflow creates a git tag via GitHub API:

prod/{MODEL_VERSION}-{YYYYMMDD}-{HHMMSS}
# Example: prod/V12-20260810-201724

This tag corresponds 1:1 with the model version set as DEFAULT in the PROD Model Registry.

Rollback

The rollback.yml workflow enables manual rollback to any previous model version.

Inputs

InputRequiredExample
model_versionYesV11
reasonYesRegression in precision metric

Rollback Steps

  1. Set DEFAULT version: ALTER MODEL ... SET DEFAULT_VERSION = 'V11'
  2. Redeploy SPCS service with rolled-back model
  3. Validate gateway endpoint responds correctly
  4. Tag rollback: rollback/V11-{timestamp}

Trigger

GitHub Actions → Rollback workflow → Run workflow (manual dispatch)

Branch Protection

  • main branch: requires PR with passing lint + test checks
  • enforce_admins: true — rules apply to all users including admins
  • Only feature/* branches can be merged to main

Network Policy

Service users are restricted to GitHub Actions IP ranges via a Snowflake network policy attached at the user level.

Environment Overrides

The CI workflow overrides database/warehouse/pool per environment via environment variables. The ml_pipeline_dag.py script reads --env stage to select the correct config:

ENV_CONFIG = {
    "dev":   {"database": "SNOW_MLOPS_DEV",   "warehouse": "SNOW_MLOPS_DEV_WH",   ...},
    "stage": {"database": "SNOW_MLOPS_STAGE", "warehouse": "SNOW_MLOPS_STAGE_WH", ...},
}

Adding a New Pipeline Step

  1. Add compute mode to PIPELINE_CONFIG: "new_step_compute": "spcs"
  2. Create a build_new_step_remote(cfg) function in ml_pipeline_dag.py
  3. Add DAGTask("NEW_STEP", definition=func) to the DAG
  4. Wire dependencies: eval_task >> new_task

Key Lessons Learned

IssueRoot CauseFix
